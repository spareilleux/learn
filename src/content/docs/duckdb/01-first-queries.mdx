## Installing the CLI

[DuckDB](https://duckdb.org/) is a library: it runs inside the process that uses it, like SQLite. The [DuckDB CLI](https://duckdb.org/docs/current/clients/cli/overview) is one such process, a single executable with no dependencies. It's the quickest way to start, and the one this course uses until lesson 5.

<Tabs syncKey="os">
<TabItem label="Windows">

```powershell
winget install DuckDB.cli
```

Open a new terminal afterwards so `duckdb` is on the `PATH`. The [CI of this course](https://github.com/spareilleux/learn/blob/main/.github/workflows/duckdb-examples.yml) downloads `duckdb_cli-windows-amd64.zip` from the [GitHub releases](https://github.com/duckdb/duckdb/releases) instead, to pin the version: the executable only needs to be unzipped.

</TabItem>
<TabItem label="Linux / WSL">

```bash
curl https://install.duckdb.org | sh
```

The script installs the binary in `~/.duckdb/cli/<version>/`, points `~/.duckdb/cli/latest` to it, and prints the line to add to your shell profile:

```bash
export PATH="$HOME/.duckdb/cli/latest":$PATH
```

If `~/.local/bin` exists, it also creates a `duckdb` link there. On a GitHub runner: `Successfully installed DuckDB 1.5.5 to /home/runner/.duckdb/cli/1.5.5/duckdb`. Set `DUCKDB_VERSION=1.5.5` before `sh` to pin the version.

</TabItem>
<TabItem label="macOS">

```bash
brew install duckdb
```

Or the same script as on Linux, which the CI of this course uses on `macos-latest`:

```bash
curl https://install.duckdb.org | sh
```

</TabItem>
</Tabs>

```bash
duckdb --version
```

## A query on a file

Start the CLI with `duckdb`: it answers with its version and `Enter ".help" for usage hints.`, and an in-memory database. Then, without creating anything:

```sql
DESCRIBE FROM 'data/runs.json';
```

```text
┌────────────────────────┐
│     data/runs.json     │
│                        │
│ attempt      bigint    │
│ conclusion   varchar   │
│ createdAt    timestamp │
│ databaseId   bigint    │
│ event        varchar   │
│ headBranch   varchar   │
│ headSha      varchar   │
│ startedAt    timestamp │
│ status       varchar   │
│ updatedAt    timestamp │
│ workflowName varchar   │
└────────────────────────┘
```

A file name in quotes is a table. DuckDB saw the `.json` extension, read the file, and inferred a type for each field: `bigint` for the numbers, `timestamp` for the ISO 8601 strings, `varchar` for the rest. In SQL Server, the closest thing is [`OPENROWSET(BULK …)`](https://learn.microsoft.com/sql/t-sql/functions/openrowset-bulk-transact-sql) with `OPENJSON` and an explicit `WITH` clause listing the columns and their types.

`DESCRIBE FROM 'data/runs.json'` is also a first taste of DuckDB's [friendly SQL](https://duckdb.org/docs/current/sql/dialect/friendly_sql): `FROM` can come first, and a query with only `FROM` means `SELECT *`.

The first query of [`sql/01-first-queries.sql`](https://github.com/spareilleux/learn/blob/main/code/duckdb/sql/01-first-queries.sql): which workflows run most, and how often they fail.

```sql
SELECT workflowName, count(*) AS runs, count(*) FILTER (conclusion = 'failure') AS failures
FROM 'data/runs.json'
GROUP BY ALL
ORDER BY runs DESC, workflowName
LIMIT 5;
```

```text
┌────────────────────────┬───────┬──────────┐
│      workflowName      │ runs  │ failures │
│        varchar         │ int64 │  int64   │
├────────────────────────┼───────┼──────────┤
│ Deploy to GitHub Pages │    65 │        2 │
│ Rust course examples   │    18 │        3 │
│ Java course examples   │     7 │        0 │
│ GHA 03: triggers       │     5 │        2 │
│ GHA 07: security       │     4 │        0 │
└────────────────────────┴───────┴──────────┘
```

Two extensions to the SQL you know:

- [`GROUP BY ALL`](https://duckdb.org/docs/current/sql/query_syntax/groupby) groups by every column of the `SELECT` that isn't an aggregate. No more copying the column list into `GROUP BY`.
- [`FILTER`](https://duckdb.org/docs/current/sql/query_syntax/filter) restricts one aggregate. The SQL Server way is `sum(CASE WHEN conclusion = 'failure' THEN 1 ELSE 0 END)`. `FILTER` is standard SQL, and PostgreSQL has it too.

`LIMIT` is `TOP` at the end of the query. The output format is `duckbox`, the CLI's default: column types under the names, and numbers aligned right.

## Reading the errors

A PostgreSQL habit, `snake_case` column names:

```sql
SELECT workflow_name FROM 'data/runs.json';
```

```text
Binder Error: Referenced column "workflow_name" not found in FROM clause!
Candidate bindings: "workflowName", "conclusion"

LINE 1: SELECT workflow_name FROM 'data/runs.json';
               ^
```

A **Binder Error** means the SQL parsed, but a name doesn't resolve. DuckDB suggests the closest names and points at the position. A table that doesn't exist yet gives a **Catalog Error**:

```sql
FROM runs;
```

```text
Catalog Error: Table with name runs does not exist!
Did you mean "duckdb_constraints"?

LINE 1: FROM runs;
             ^
```

The suggestion is the closest name among the system views: a guess, not a hint that something is wrong with `duckdb_constraints`.

## First look at the data: `SUMMARIZE`

[`SUMMARIZE`](https://duckdb.org/docs/current/guides/meta/summarize) computes statistics for every column. It returns 12 columns, too wide for this page; since its result is a table like any other, a query can pick some:

```sql
SELECT column_name, column_type, min, max, approx_unique, null_percentage
FROM (SUMMARIZE FROM 'data/runs.json');
```

```text
┌──────────────┬─────────────┬──────────────────────────────────────────┬──────────────────────────────────────────┬───────────────┬─────────────────┐
│ column_name  │ column_type │                   min                    │                   max                    │ approx_unique │ null_percentage │
│   varchar    │   varchar   │                 varchar                  │                 varchar                  │     int64     │  decimal(9,2)   │
├──────────────┼─────────────┼──────────────────────────────────────────┼──────────────────────────────────────────┼───────────────┼─────────────────┤
│ attempt      │ BIGINT      │ 1                                        │ 3                                        │             2 │            0.00 │
│ conclusion   │ VARCHAR     │ cancelled                                │ success                                  │             4 │            0.00 │
│ createdAt    │ TIMESTAMP   │ 2026-09-13 15:53:16                      │ 2026-09-14 14:01:09                      │            93 │            0.00 │
│ databaseId   │ BIGINT      │ 34766934801                              │ 34852867099                              │           131 │            0.00 │
│ event        │ VARCHAR     │ push                                     │ workflow_dispatch                        │             2 │            0.00 │
│ headBranch   │ VARCHAR     │ gha-06-invalid                           │ main                                     │             2 │            0.00 │
│ headSha      │ VARCHAR     │ 04c8770830c5666ca1e9bb8a4711065edfb351b4 │ fd52d46d1d2940e5dee33790e4a2873056f074f3 │            59 │            0.00 │
│ startedAt    │ TIMESTAMP   │ 2026-09-13 15:53:16                      │ 2026-09-14 14:01:09                      │            94 │            0.00 │
│ status       │ VARCHAR     │ completed                                │ completed                                │             1 │            0.00 │
│ updatedAt    │ TIMESTAMP   │ 2026-09-13 15:53:55                      │ 2026-09-14 14:03:38                      │           122 │            0.00 │
│ workflowName │ VARCHAR     │ Deploy to GitHub Pages                   │ WSL containers examples                  │            17 │            0.00 │
└──────────────┴─────────────┴──────────────────────────────────────────┴──────────────────────────────────────────┴───────────────┴─────────────────┘
  11 rows                                                                                                                                  6 columns
```

What this says in a few seconds:

- 125 rows and no `NULL` anywhere: the snapshot only has completed runs (`status` has one value).
- The history covers less than a day: from 2026-09-13 15:53 to 2026-09-14 14:01.
- `attempt` goes up to 3: at least one run was re-run twice.
- `headBranch` has two values: `main`, and the branch of an experiment from the GitHub Actions course.
- **`approx_unique` is an estimate.** `databaseId`, the run id, is unique, yet 131 is more than the 125 rows. It uses [HyperLogLog](https://duckdb.org/docs/current/sql/functions/aggregates), which trades exactness for constant memory. Exercise 2 finds the exact counts.
- `min` and `max` are `varchar` for every column, so they fit in one result column: `max` of `attempt` is the string `'3'`.

The timestamps in the file end with `Z` (UTC). DuckDB read them as `TIMESTAMP`, without a time zone: the values are the UTC times, and nothing in the type says so. Lesson 2 comes back to this.

## Keeping the rows: a table

Each query above read and parsed the JSON file again. To read it once, store the rows in a table ([`CREATE TABLE … AS`](https://duckdb.org/docs/current/sql/statements/create_table), the `SELECT INTO` of SQL Server):

```sql
CREATE TABLE runs AS SELECT * FROM 'data/runs.json';

SELECT event, conclusion, count(*) AS runs
FROM runs
GROUP BY ALL
ORDER BY event, conclusion;
```

```text
┌───────────────────┬─────────────────┬───────┐
│       event       │   conclusion    │ runs  │
│      varchar      │     varchar     │ int64 │
├───────────────────┼─────────────────┼───────┤
│ push              │ cancelled       │     2 │
│ push              │ failure         │     7 │
│ push              │ startup_failure │     1 │
│ push              │ success         │    96 │
│ workflow_dispatch │ cancelled       │     2 │
│ workflow_dispatch │ failure         │     9 │
│ workflow_dispatch │ success         │     8 │
└───────────────────┴─────────────────┴───────┘
```

Manual runs (`workflow_dispatch`) failed 9 times out of 19; pushes, 7 out of 106. That matches how the GitHub Actions course was written: the exercise workflows, started by hand, were designed to fail.

The table lives in the in-memory database, and disappears when the CLI exits.

## Keeping the database: a file

The file name is the first argument of `duckdb`. The file is created if it doesn't exist:

```bash
mkdir out
duckdb out/ci.duckdb
```

```sql
CREATE TABLE runs AS FROM 'data/runs.json';
.quit
```

Start it again with the same file, and the table is still there:

```bash
duckdb out/ci.duckdb
```

```sql
SELECT count(*) FROM runs;
SELECT database_name, path FROM duckdb_databases() WHERE NOT internal;
```

```text
┌──────────────┐
│ count_star() │
│    int64     │
├──────────────┤
│          125 │
└──────────────┘
┌───────────────┬─────────────────────────────────────────────────────────────┐
│ database_name │                            path                             │
│    varchar    │                           varchar                           │
├───────────────┼─────────────────────────────────────────────────────────────┤
│ ci            │ C:\Users\spare\source\repos\learn\code\duckdb\out\ci.duckdb │
└───────────────┴─────────────────────────────────────────────────────────────┘
```

The database is named after the file. The `.duckdb` extension is a convention; DuckDB doesn't require it.

## Writing files: `COPY`

[`COPY … TO`](https://duckdb.org/docs/current/sql/statements/copy) writes a table or a query result to a file, and picks the format from the extension:

```sql
COPY runs TO 'out/runs.csv';
COPY runs TO 'out/runs.parquet';
```

The sizes, for the same 125 rows:

| File | Bytes |
|---|---|
| `data/runs.json` | 39,705 |
| `out/runs.csv` | 21,058 |
| `out/runs.parquet` | 8,553 |
| `out/ci.duckdb` | 536,576 |

[Parquet](https://duckdb.org/docs/current/data/parquet/overview) is a compressed, columnar file format with types, and the one lesson 4 recommends for data you keep. The `.duckdb` file is the largest. A database file with nothing in it is 12,288 bytes of headers; data is stored in blocks of 262,144 bytes (`block_size` in `PRAGMA database_size`), and this one has two: 12,288 + 2 × 262,144 = 536,576. The format is made for millions of rows, not for 125.

`COPY` doesn't create folders. Without the `mkdir out` above:

```text
IO Error: Cannot open file "out/runs.parquet": The system cannot find the path specified.
```

The second half of that message is the Windows system error text.

## Two CLI settings

Dot commands configure the CLI itself. They are not SQL, and take no semicolon ([list](https://duckdb.org/docs/current/clients/cli/dot_commands)):

```sql
.timer on
SELECT count(*) FROM 'out/runs.parquet';
```

```text
┌──────────────┐
│ count_star() │
│    int64     │
├──────────────┤
│          125 │
└──────────────┘
Run Time (s): real 0.001 user 0.000000 sys 0.000000
```

On 125 rows, every query takes about a millisecond: the timer only gets interesting in lesson 7. `.mode` changes the [output format](https://duckdb.org/docs/current/clients/cli/output_formats); `.mode line` shows one field per line, handy for wide rows:

```sql
.mode line
FROM 'data/runs.json' LIMIT 1;
```

```text
     attempt = 1
  conclusion = success
   createdAt = 2026-09-14 14:01:09
  databaseId = 34852867099
       event = push
  headBranch = main
     headSha = 95a3830ebbcfa3f0addbc1eba8335a20cc2c41f2
   startedAt = 2026-09-14 14:01:09
      status = completed

workflowName = Deploy to GitHub Pages
```

## Key takeaways

- DuckDB is a library that runs in your process; the CLI is one executable, and needs no server.
- A quoted file name is a table: DuckDB infers the format from the extension and the types from the content.
- `DESCRIBE` and `SUMMARIZE` are the first two commands to run on unknown data; `approx_unique` is an estimate.
- A table stays in memory unless the CLI was started with a database file; `COPY … TO` writes CSV, JSON or Parquet.
- Errors name their kind (`Binder`, `Catalog`, `IO`) and suggest the closest names.

## Exercises

The solutions are in [`sql/01-exercises.sql`](https://github.com/spareilleux/learn/blob/main/code/duckdb/sql/01-exercises.sql), checked by CI like the lesson.

1. How many manual runs (`workflow_dispatch`) failed?

<details>
<summary>Solution</summary>

```sql
SELECT count(*) AS failed_manual_runs
FROM 'data/runs.json'
WHERE event = 'workflow_dispatch' AND conclusion = 'failure';
```

```text
┌────────────────────┐
│ failed_manual_runs │
│       int64        │
├────────────────────┤
│                  9 │
└────────────────────┘
```

The same number as the `workflow_dispatch` / `failure` row of the table above.

</details>

2. `SUMMARIZE` estimates 17 distinct workflow names and 59 distinct commits. What are the exact numbers?

<details>
<summary>Solution</summary>

```sql
SELECT count(DISTINCT workflowName) AS workflows, count(DISTINCT headSha) AS commits
FROM 'data/runs.json';
```

```text
┌───────────┬─────────┐
│ workflows │ commits │
│   int64   │  int64  │
├───────────┼─────────┤
│        21 │      65 │
└───────────┴─────────┘
```

21 and 65: the estimate was low by about 10% on both, and high by 5% on the run ids. `count(DISTINCT …)` is exact but has to remember every value it has seen; `approx_count_distinct(…)` gives the same kind of estimate as `SUMMARIZE` in constant memory. On 125 rows, use the exact one.

</details>

3. The Binder Error above suggested `workflowName`. Would `workflowname`, all lowercase, work? And what would the column be called in the result?

<details>
<summary>Solution</summary>

```sql
SELECT workflowname, count(*) AS runs
FROM 'data/runs.json'
WHERE workflowname LIKE 'GHA 0%'
GROUP BY ALL
ORDER BY workflowname
LIMIT 3;
```

```text
┌─────────────────────────┬───────┐
│      workflowName       │ runs  │
│         varchar         │ int64 │
├─────────────────────────┼───────┤
│ GHA 01: hello           │     1 │
│ GHA 02: build and test  │     3 │
│ GHA 02: exercise checks │     1 │
└─────────────────────────┴───────┘
```

Yes. [Identifiers are case-insensitive](https://duckdb.org/docs/current/sql/dialect/keywords_and_identifiers) in DuckDB, "similarly to PostgreSQL", and also in double quotes, unlike PostgreSQL where `"workflowName"` and `workflowname` are two different names. The comparison is ASCII-only: `é` and `É` are different letters for it. DuckDB preserves the case of the name as it was defined, so the result column is `workflowName`, not the case typed in the query. `workflow_name` failed because the underscore makes it a different name, not because of the case.

</details>
