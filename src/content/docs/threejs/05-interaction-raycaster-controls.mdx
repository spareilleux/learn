## Hit testing, in three toolkits

A 3D scene doesn't know where the pointer is. WPF does the work for you: [`VisualTreeHelper.HitTest`](https://learn.microsoft.com/dotnet/api/system.windows.media.visualtreehelper.hittest) on a `Viewport3D` returns a [`RayMeshGeometry3DHitTestResult`](https://learn.microsoft.com/dotnet/api/system.windows.media.media3d.raymeshgeometry3dhittestresult) with the mesh, the point and the triangle. JavaFX puts a [`PickResult`](https://openjfx.io/javadoc/25/javafx.graphics/javafx/scene/input/PickResult.html) in every mouse event. MonoGame gives you the pieces: [`Viewport.Unproject`](https://docs.monogame.net/api/Microsoft.Xna.Framework.Graphics.Viewport.html) to turn a screen point into two points in the world, a [`Ray`](https://docs.monogame.net/api/Microsoft.Xna.Framework.Ray.html) between them, and `Ray.Intersects` against bounding boxes and spheres, never against triangles.

three.js is in between. [`Raycaster`](https://threejs.org/docs/pages/Raycaster.html) turns a pointer position into a ray from the camera, and tests it against the triangles of meshes; wiring the pointer events is your job.

| | WPF 3D | MonoGame | JavaFX 3D | three.js |
|---|---|---|---|---|
| Input | a point in the `Viewport3D` | a point in the window | a mouse event | normalized device coordinates, −1 to 1 |
| Tested against | `ModelVisual3D` triangles | `BoundingBox`, `BoundingSphere`, `Plane` | `Node` triangles | `Mesh` triangles, `Points` and `Line` within a threshold, sprites |
| Result | the nearest hit, or a callback per hit | a distance | the nearest node, point, face and texture coordinate | every hit, sorted by distance: object, point, face, UV, instance |
| Skipping objects | `IsHitTestVisible` | your code | `mouseTransparent` | layers, or the list of objects you pass |

## The scene: a fretboard to point at

[`fretboard.ts`](https://github.com/spareilleux/learn/blob/8bf126b/code/threejs/src/05-picking/fretboard.ts) builds the neck of lesson 2 again, longer: a box, 12 frets and 6 strings, all in one `Group`. The frets follow the rule of a real guitar, each one a twelfth root of two closer to the bridge ([line 16](https://github.com/spareilleux/learn/blob/8bf126b/code/threejs/src/05-picking/fretboard.ts#L16)), so a point's X gives the fret back with a logarithm, and its Z gives the nearest string ([lines 20-36](https://github.com/spareilleux/learn/blob/8bf126b/code/threejs/src/05-picking/fretboard.ts#L20-L36)):

```ts
// Where a finger at x presses: 0 before the nut side of fret 1, n between fret n − 1 and fret n
export function fretAt(x: number): number | null {
  if (x < NUT_X || x > fretX(FRETS)) return null;
  return Math.ceil(-12 * Math.log2(1 - (x - NUT_X) / SCALE));
}
```

The file imports nothing from the DOM, so the page and a Node.js script share it.

## From a pointer event to a ray

A `Raycaster` wants the pointer in **normalized device coordinates** (NDC): −1 at the left edge of the canvas, +1 at the right, +1 at the top and −1 at the bottom, whatever its size in pixels. The page computes them from the canvas's own rectangle ([`main.ts`, lines 35-44](https://github.com/spareilleux/learn/blob/8bf126b/code/threejs/src/05-picking/main.ts#L35-L44)):

```ts
// The pointer in normalized device coordinates (−1 to 1), from the canvas's own rectangle
const pointer = new THREE.Vector2();
let pointerInside = false;
let pointerMoved = false;
renderer.domElement.addEventListener('pointermove', (event) => {
  const rect = renderer.domElement.getBoundingClientRect();
  pointer.set(((event.clientX - rect.left) / rect.width) * 2 - 1, -((event.clientY - rect.top) / rect.height) * 2 + 1);
  pointerInside = true;
  pointerMoved = true;
});
```

Y is flipped: the DOM counts down from the top, NDC counts up. [`setFromCamera`](https://github.com/mrdoob/three.js/blob/r186/src/core/Raycaster.js#L119-L139) then starts the ray at the camera's position and points it through the pointer, by unprojecting the point `(x, y, 0.5)` with the camera's matrices. For an orthographic camera, every ray is parallel and starts in the camera's plane.

Then `intersectObject` tests the ray, and the first hit gives the fret, the string and the note ([lines 59-73](https://github.com/spareilleux/learn/blob/8bf126b/code/threejs/src/05-picking/main.ts#L59-L73)):

```ts
function pick(ndc: THREE.Vector2): Pick {
  raycaster.setFromCamera(ndc, camera);
  // Recursive: the fretboard group's children are the neck, the frets and the strings
  const [hit] = raycaster.intersectObject(board, true);
  if (!hit) return null;
  const fret = fretAt(hit.point.x);
  const string = stringAt(hit.point.z);
  return {
    object: hit.object.name,
    point: hit.point.toArray().map((n) => Number(n.toFixed(3))),
    fret,
    string,
    note: fret === null ? null : noteName(string, fret),
  };
}
```

## What a ray finds, without a browser

`Raycaster` is plain math on the CPU: no renderer, no GPU, no DOM. [`scripts/l05-raycaster.ts`](https://github.com/spareilleux/learn/blob/8bf126b/code/threejs/scripts/l05-raycaster.ts) builds the same fretboard and camera in Node.js, and shoots rays at it:

```text
$ node scripts/l05-raycaster.ts
pointer (NDC): [ -0.1894, 0.0006 ]
ray origin [ -0.2, 2.4, 1.6 ] direction [ -0.122, -0.789, -0.602 ]
intersectObject(board, true): neck at 2.584
first hit: { point: [ -0.514, 0.36, 0.045 ], faceIndex: 4, uv: [ 0.413, 0.418 ] }
fret 5, string 3: C4
intersectObject(board, false): (none)
over string 1: string 1 at 2.598 | neck at 2.648
strings on layer 1: neck at 2.648
raycaster.layers.enable(1): string 1 at 2.598 | neck at 2.648
far = 2: (none)
ray.intersectPlane: [ -0.514, 0.36, 0.045 ]
over fret 4, InstancedMesh: frets (instanced) at 2.531, instance 3
10,000 × intersectObject(board, true): N µs per ray
10,000 × ray.intersectPlane: N µs per ray
```

Line by line:

- The point where a finger presses string 3 at fret 5 projects to NDC (−0.19, 0.0006): left of the center, at mid-height. The ray leaves the camera at (−0.2, 2.4, 1.6), and meets the top of the neck 2.584 units away, at (−0.514, 0.36, 0.045): fret 5, string 3, C4.
- Each hit carries the point, the distance, the triangle's index (`faceIndex`) and the texture coordinate at that point (`uv`), interpolated from the triangle's vertices.
- `intersectObject(board, false)` finds nothing: the `Group` itself has no geometry, and without `recursive` its children aren't tested.
- Over string 1, the ray meets the string first, then the neck behind it: the array holds **every** hit along the ray, sorted by distance, not only the nearest one.
- An object on layer 1 is skipped: `Raycaster` tests an object only if its [layers](https://threejs.org/docs/pages/Layers.html) share one with the raycaster's ([`Raycaster.js`, lines 240-250](https://github.com/mrdoob/three.js/blob/r186/src/core/Raycaster.js#L240-L250)). It doesn't test `visible`: an invisible mesh is still hit, which exercise 1 turns into a feature.
- `far = 2` ignores everything farther than 2 units, and the neck is 2.584 away.
- Against a mathematical plane at the height of the neck, `ray.intersectPlane` gives the same point, with no mesh at all.
- With the frets as one [`InstancedMesh`](https://threejs.org/docs/pages/InstancedMesh.html), the hit says which instance: `instanceId` 3 is fret 4.
- The cost, on the author's machine: a few microseconds per ray against the 19 meshes, a few hundredths of a microsecond against the plane. Each mesh is first tested against its bounding sphere, then triangle by triangle. `check.sh` replaces the numbers with N, since they change with every run.

Two details of the script matter in any code that raycasts outside a render loop. A page renders before it raycasts, and rendering updates the objects' world matrices; a script, a test or an event handler that runs before the first frame must call `updateMatrixWorld()` itself. And the camera, which isn't in the scene, needs it too: without `camera.updateMatrixWorld()`, the first version of this script projected the press point to an NDC of −3.6, far outside the canvas.

### Controls

```ts
const controls = new OrbitControls(camera, renderer.domElement);
controls.target.set(-0.2, 0.3, 0);
controls.enableDamping = params.has('damping');
controls.update();
```

`OrbitControls` lives in `three/addons/controls/OrbitControls.js`, not in the core. It listens to `pointerdown` on the canvas, then captures the pointer (`setPointerCapture`) and listens to `pointermove` and `pointerup` on the document, so a drag that leaves the canvas keeps turning ([lines 1553-1564](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/controls/OrbitControls.js#L1553-L1564)). It sets `touch-action: none` on the canvas, so that a finger turns the camera instead of scrolling the page. With `enableDamping`, the camera keeps moving for a while after the drag: `controls.update()` must then run every frame, which the loop does. `controls.dispose()` removes the listeners ([lines 512-538](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/controls/OrbitControls.js#L512-L538)); a component that creates controls and never disposes them leaves those listeners behind.

The addons have other controls, with the same constructor: `MapControls` (panning first, as in a map), `TrackballControls` (no fixed up direction), `PointerLockControls` (first person), `TransformControls` (a gizmo to move an object) and `DragControls`.

## In GuitarAlchemist/ga

GA has `Raycaster` in 14 files. All of them compute NDC from the canvas's rectangle, so the sidebar bug above isn't there. The differences are in when they raycast, and what they clean up.

- **A listener per effect run.** `ThreeHeadstock.tsx` adds its click handler with `canvas.addEventListener('click', handleClick)` in `setupMouseInteraction` ([lines 698-744](https://github.com/GuitarAlchemist/ga/blob/05c8eda013f2a4d11efaa52c4ca94674521ee684/ReactComponents/ga-react-components/src/components/ThreeHeadstock.tsx#L698-L744)), called from a `useEffect` whose dependencies include the guitar model, the style, the tuning, the width and the height ([line 178](https://github.com/GuitarAlchemist/ga/blob/05c8eda013f2a4d11efaa52c4ca94674521ee684/ReactComponents/ga-react-components/src/components/ThreeHeadstock.tsx#L178)). ## Live demo: a whole guitar

The same two steps on a whole guitar, modeled in code rather than loaded: the body and the headstock are extruded outlines, and the frets, inlays, pole pieces, saddles and tuners are instanced meshes. A ray against an invisible box over the fretboard, then its crossing with the plane of the strings, gives a fret from its x coordinate and a string from its z coordinate, with lesson 13's `fretAtX` and `noteAt`. A click plucks the string, which vibrates in its vertex shader, and plays the note through a small Karplus-Strong synthesizer on the Web Audio API. Its probe clicks string 3 at fret 5 with Playwright's mouse and reads `string 3, fret 5: C4`, with 32 draw calls and 47,405 triangles. The [source](https://github.com/spareilleux/learn/tree/f68e710/code/threejs/demos/guitar) is in `code/threejs/demos/guitar`.

## Key takeaways

- `Raycaster.setFromCamera` takes normalized device coordinates: compute them from the canvas's `getBoundingClientRect()`, not from the window.
- `intersectObject(object, true)` returns every hit along the ray, nearest first, with point, distance, face, UV and, for instanced meshes, `instanceId`.
- The raycaster tests layers, not `visible`; `far`, `near` and the list of objects you pass limit the work.
- Raycasting is CPU math: test it in Node.js, but update the world matrices yourself, the camera's included.
- Raycast from the frame loop, once, when the pointer moved; remove your listeners and dispose controls when the component goes.

<summary>Solution 2</summary>

```text
threshold 1: 3 hit(s), nearest to the ray: index 2, first: index 3
threshold 0.1: 1 hit(s), nearest to the ray: index 2, first: index 2
threshold 0.05: 1 hit(s), nearest to the ray: index 2, first: index 2

```

For `Points`, a hit is a point whose distance to the ray is below `raycaster.params.Points.threshold`, in world units; the default is 1, larger than this whole fretboard's width. With 1, three of the four dots count, and `hits[0]` is the one **nearest the camera** along the ray, index 3 (fret 7), not the one nearest the ray: each hit has a `distanceToRay` to sort by. From 0.1 down to 0.05, only the dot at fret 5 is left; at 0.02, the ray passes 0.04 away and nothing is hit. `Line` has the same parameter, `params.Line.threshold`. With `PointsMaterial.sizeAttenuation`, a dot's size on screen changes with distance but the threshold doesn't: a threshold in pixels needs your own conversion.

</details>

<details>
<summary>Solution 3</summary>

It depends on where the pointer is, not only on the sidebar. The window-based NDC is `clientX / innerWidth`, the correct one is `(clientX − left) / width`: the error grows with the panel and shrinks toward the right edge of the window, where both reach 1. With a 480-pixel panel, the canvas would be 320 pixels wide, and the pointer at string 3 fret 5 would be at a different `clientX` too, so the wrong fret can't be read from the first result. Reasoned, not measured: run the page with a wider `.sidebar` to check (*to verify*).

</details>
