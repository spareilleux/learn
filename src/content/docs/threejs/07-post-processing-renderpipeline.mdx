## Post-processing, in three toolkits

Post-processing draws the scene into a texture instead of the screen, then runs pixel shaders on that texture: bloom, anti-aliasing, depth of field, color grading. In MonoGame, you do it by hand: `GraphicsDevice.SetRenderTarget` with a [`RenderTarget2D`](https://docs.monogame.net/api/Microsoft.Xna.Framework.Graphics.RenderTarget2D.html), draw the scene, then draw the texture on a full-screen quad through an `Effect`. WPF applies a [`ShaderEffect`](https://learn.microsoft.com/dotnet/api/system.windows.media.effects.shadereffect) to an element's rendered pixels, including a `Viewport3D`'s.

three.js had `EffectComposer` for `WebGLRenderer`: a list of passes, each a `ShaderMaterial` drawn on a quad. `WebGPURenderer` replaces it with [`RenderPipeline`](https://threejs.org/docs/pages/RenderPipeline.html), where the effects are TSL nodes of lesson 6, connected in a graph.

| | MonoGame | three.js, `WebGLRenderer` | three.js, `WebGPURenderer` |
|---|---|---|---|
| The chain | your code, target by target | `EffectComposer`, a list of passes | `RenderPipeline`, a graph of nodes |
| Rendering the scene | `SetRenderTarget`, then draw | `RenderPass` | `pass(scene, camera)` |
| An effect | an `Effect` on a quad | `UnrealBloomPass`, `ShaderPass(shader)` | `bloom(node)`, `fxaa(node)`, any TSL node |
| Tone mapping and sRGB | your last shader | `OutputPass`, added by hand | applied by the pipeline, unless `outputColorTransform = false` |
| Each frame | `Draw` | `composer.render()` | `pipeline.render()`, instead of `renderer.render()` |

`RenderPipeline` was called `PostProcessing` until r183. The old name still works, with a warning: "PostProcessing: "PostProcessing" has been renamed to "RenderPipeline". Please update your code to use "THREE.RenderPipeline" instead." ([`PostProcessing.js`, lines 5-20](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/PostProcessing.js#L5-L20)).

## Bloom on the inlays

The fretboard gets five inlays that emit light, with an emissive intensity of 6: far above 1, the brightest a pixel can show after tone mapping. Bloom takes the pixels above a threshold, blurs them at several sizes, and adds the blur to the image, so bright things glow as they do through a camera lens ([lines 46-62](https://github.com/spareilleux/learn/blob/8bf126b/code/threejs/src/07-post/main.ts#L46-L62)):

```ts
// The chain, as a graph of nodes: the scene pass's color texture, bloom added on top, then the output transform
let pipeline: THREE.RenderPipeline | null = null;
let direct: THREE.DirectRenderPipeline | null = null;
const disposables: { dispose(): void }[] = [];
if (mode === 'bloom' || mode === 'bloom-fxaa') {
  pipeline = new THREE.RenderPipeline(renderer);
  const scenePass = pass(scene, camera);
  const sceneColor = scenePass.getTextureNode('output');
  const glow = bloom(sceneColor, 1.2, 0.4, threshold);
  disposables.push(scenePass, glow);
  if (mode === 'bloom') {
    pipeline.outputNode = sceneColor.add(glow);
  } else {
    // FXAA expects tone-mapped sRGB values: the pipeline's own output transform is turned off and applied before FXAA
    pipeline.outputColorTransform = false;
    pipeline.outputNode = fxaa(renderOutput(sceneColor.add(glow)));
  }
}
```

`pass(scene, camera)` renders the scene into a render target, and `getTextureNode('output')` is its color, as a node. [`bloom(node, strength, radius, threshold)`](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/BloomNode.js#L585-L597) comes from `three/addons/tsl/display/BloomNode.js`; the addons have about fifty such nodes in the same folder, from `fxaa` and `smaa` to `ssao`, `ssr`, `dof` and `outline`. `sceneColor.add(glow)` is TSL: the final image is the scene plus its glow. The pipeline renders that graph on a full-screen quad, then applies the renderer's tone mapping and sRGB conversion, since `outputColorTransform` is `true` by default.

The page's loop calls `pipeline.render()` instead of `renderer.render(scene, camera)`: the scene is rendered by the pass, inside the pipeline.

| `?pipeline=` | calls, 3 frames | draw calls | render targets | programs | halo, 0.06 away | neck, 0.15 away | background |
|---|---|---|---|---|---|---|---|
| `none` | 6 | 25 | 1 | 4 | 53, 28, 20 | 53, 28, 20 | 12, 15, 20 |
| `bloom` | 42 | 37 | 12 | 13 | 127, 168, 190 | 74, 81, 94 | 13, 17, 23 |
| `bloom-fxaa` | 45 | 38 | 13 | 15 | 132, 174, 195 | 74, 82, 96 | 13, 17, 23 |
| `direct` | 3 | 25 | 0 | 4 | 53, 28, 20 | 53, 28, 20 | 12, 15, 20 |

Without bloom, the neck beside the inlay is the same brown as anywhere else. With it, the halo turns the neck light blue at 0.06 units, still tints it at 0.15, and even lifts the background by a few levels. The price is in the other columns:

- **Draw calls: 37 instead of 25.** The 24 objects are drawn once, into the scene pass. Then come 13 full-screen quads: one to keep the bright pixels, five blurred horizontally and five vertically at halving sizes, one to combine them, and the pipeline's output quad. Per frame, the `calls` count 14 renders instead of 2.
- **Render targets: 12 instead of 1.** The scene pass has one; `BloomNode` creates eleven, one for the bright pixels and a horizontal and a vertical one for each of its five sizes ([`BloomNode.js`, lines 156-180](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/BloomNode.js#L156-L180)). They are half-float textures, sized from the canvas: memory that grows with the screen.
- **Programs: 13 instead of 4.** Each step is a shader.

FXAA adds one pass, one render target and two programs. The table comes from WebGPU. On the WebGL 2 backend, the bloom chains count one more program, 14 and 16, and on the CI runners without a GPU, which render with SwiftShader on the CPU, FXAA's halo pixel reads 135, 176, 197: 3 more than here, beyond the difference of 2 per channel that `compare.mjs` accepts. `check.sh` keeps those WebGL 2 outputs in `expected/*.webgl.txt`.

### FXAA, after the output transform

FXAA smooths jagged edges by looking at the contrast between neighboring pixels, and "requires sRGB input", says its source: tone mapping and the sRGB conversion must come first ([`FXAANode.js`, lines 5-6](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/FXAANode.js#L5-L6)). So the page turns the pipeline's own output transform off, and applies it inside the graph with `renderOutput`, before `fxaa`. The renderer is created with `antialias: false` in that mode: MSAA on the scene pass and FXAA after it would do the work twice.

## DirectRenderPipeline: no output pass

Even without effects, `WebGPURenderer` renders into a render target, then copies it to the screen through an output pass that does the tone mapping and the sRGB conversion: the `none` row has 1 render target and 2 calls per frame. r186 adds [`DirectRenderPipeline`](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/DirectRenderPipeline.js), which "applies output processing directly in material shaders", avoiding "the intermediate framebuffer and output pass", but "changes blending and is not compatible with materials that sample the framebuffer, such as transmissive materials" ([lines 6-20](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/DirectRenderPipeline.js#L6-L20)). Its `render` takes the scene and the camera, unlike `RenderPipeline`'s:

```text
$ node scripts/probe.mjs 07-post --query pipeline=direct
{
  "frame": 4,
  "render": {
    "calls": 3,
    "drawCalls": 25,
    "triangles": 2924
  },
  "memory": {
    "geometries": 10,
    "textures": 1,
    "programs": 4
  },
  "pipeline": "direct",
  "threshold": 1,
  "renderTargets": 0,
  "pixels": {
    "inlay at fret 5": "rgb(242, 250, 252)",
    "halo, 0.06 beside it": "rgb(53, 28, 20)",
    "neck, 0.15 beside it": "rgb(53, 28, 20)",
    "background": "rgb(12, 15, 20)"
  }

```

The same four pixels as `none`, with 0 render targets and one call per frame. The draw calls stay at 25, but the 25th is no longer a quad: a solid `scene.background` becomes a sphere of 1,984 triangles drawn behind the scene ([`DirectRenderPipeline.js`, lines 156-175](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/DirectRenderPipeline.js#L156-L175), and [`Background.js`, line 131](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/Background.js#L131)), hence 2,924 triangles instead of 941. On a phone, one less full-screen copy per frame can matter; measure it on the device (*to verify*).

## What dispose() frees

A component that creates a pipeline must free it when it goes. The page's `?dispose=` mode disposes after three frames and counts the render targets:

```text

    "triangles": 953

    "geometries": 10,
    "textures": 1,
    "programs": 2

  "renderTargets": {
    "before": 12,
    "afterPipelineDispose": 12,

```

`pipeline.dispose()` frees one program, its output quad's material, and none of the 12 render targets: it disposes only that material ([`RenderPipeline.js`, lines 162-169](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/RenderPipeline.js#L162-L169)). The render targets belong to the nodes, and go only when the scene pass and the bloom node are disposed too: 0 render targets, 1 texture and 2 programs left. So keep a reference to every node that owns a render target, and dispose them with the pipeline.

## Key takeaways

- With `WebGPURenderer`, post-processing is `RenderPipeline`: a graph of TSL nodes that starts with `pass(scene, camera)`, rendered by `pipeline.render()`. `PostProcessing` is its pre-r183 name.
- Every effect costs draw calls, programs and render targets that scale with the canvas: bloom took 13 more quads and 11 more render targets here.
- Effects that expect sRGB, like FXAA, come after `renderOutput`, with `outputColorTransform = false`.
- `DirectRenderPipeline` removes the output pass when no effect is needed, with limits on blending and transmission.
- `pipeline.dispose()` doesn't free the passes' render targets: dispose each node that owns one.

Counts don't change: the same passes run whatever the threshold.

<details>
<summary>Solution 2</summary>

`BloomNode` sizes its targets at half the drawing buffer (`_resolutionScale = 0.5`), then halves the size for each of its five levels ([`BloomNode.js`, lines 322-341](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/BloomNode.js#L322-L341)). The targets are `HalfFloatType`, four channels of 2 bytes each, without a depth buffer ([lines 164-180](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/BloomNode.js#L164-L180)). At 3840 × 2160, the first horizontal target is 1920 × 1080 × 8 bytes: 16,588,800 bytes, about 16.6 MB. The bright-pixel target has the same size, and each level's horizontal and vertical targets are a quarter of the level above: 1 + 2 × (1 + 1/4 + 1/16 + 1/64 + 1/256) ≈ 3.66 times 16.6 MB, about 61 MB for the bloom alone, before the scene pass. These are computed from the source, not measured in GPU memory.

`setPixelRatio(2)` on a 1920 × 1080 CSS canvas gives the same 3840 × 2160 drawing buffer. The lesson's pages cap the ratio at 2; GA's `ThreeFretboard.tsx` allows up to 6, which is 36 times the pixels of a ratio of 1, and 9 times those of a ratio of 2.

</details>

<details>
<summary>Solution 3</summary>

```ts
import { pass } from 'three/tsl';
import { bloom } from 'three/addons/tsl/display/BloomNode.js';
import { chromaticAberration } from 'three/addons/tsl/display/ChromaticAberrationNode.js';

const pipeline = new THREE.RenderPipeline(renderer);
const scenePass = pass(scene, camera);
const color = scenePass.getTextureNode('output');
const glow = bloom(color, 0.6, 0.6, 0.5);
const aberrated = chromaticAberration(color.add(glow));
pipeline.outputNode = aberrated;
```

The strength, radius and threshold are the ones ForceRadiant passes to `UnrealBloomPass` on desktop. `chromaticAberration(node, strength = 1.0, center = null, scale = 1.1)` is in `three/addons/tsl/display/ChromaticAberrationNode.js` ([lines 152-163](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/ChromaticAberrationNode.js#L152-L163)). This sketch passes `tsc` against r186's types, but was not rendered: the strength that matches ForceRadiant's `ShaderPass` is *to verify* on the page. Keep `scenePass`, `glow` and `aberrated` to dispose them with the pipeline.
