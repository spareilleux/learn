## El frontend con `mockIPC`

`@tauri-apps/api/mocks` sustituye la capa IPC en un DOM simulado: `invoke` llama a una función del test en lugar de a Rust. Vitest se ejecuta con la configuración Vite de la lección 19, con [jsdom](https://github.com/jsdom/jsdom) (de [`vite.config.ts`, líneas 26-30](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/vite.config.ts#L26-L30)):

```ts
  test: {
    // Un DOM simulado: sin webview ni Rust, mockIPC responde a invoke
    environment: "jsdom",
    include: ["src/**/*.test.ts"],
  },
```

Un test comprueba lo que envía la página y cómo lee la respuesta (de [`frontend/src/api.test.ts`, líneas 11-22](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/frontend/src/api.test.ts#L11-L22)):

```ts
test("spellChord sends the symbol and returns the command's value", async () => {
  const calls: [string, unknown][] = [];
  mockIPC((cmd, args) => {
    calls.push([cmd, args]);
    return { symbol: "Am7", qualityName: "minor seventh", notes: ["A", "C", "E", "G"], intervals: ["1", "b3", "5", "b7"] };
  });

  const chord = await api.spellChord("Am7");

  expect(calls).toEqual([["spell_chord", { symbol: "Am7" }]]);
  expect(chord.notes).toEqual(["A", "C", "E", "G"]);
});
```

El canal de la lección 18 también funciona: el mock recibe el propio objeto `Channel` y puede llamar a su `onmessage` (de [`frontend/src/api.test.ts`, líneas 37-44](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/frontend/src/api.test.ts#L37-L44)):

```ts
test("findVoicings passes each channel message to the callback", async () => {
  mockIPC((cmd, args) => {
    if (cmd !== "find_voicings") return;
    const { onEvent, maxSpan } = args as { onEvent: Channel<SearchEvent>; maxSpan: number };
    onEvent.onmessage({ event: "voicings", data: { frets: ["x32010"] } });
    onEvent.onmessage({ event: "finished", data: { found: 1, elapsedMs: 3, cancelled: false } });
    return maxSpan;
  });
```

Dos límites, ambos encontrados al escribir esta lección:

- **Vitest no comprueba los tipos.** Mientras `elapsedMs` seguía siendo un `bigint` (lección 19), el tercer test pasaba, y `tsc` rechazaba el mismo archivo: `frontend/src/api.test.ts(42,62): error TS2322: Type 'number' is not assignable to type 'bigint'.` El `npm run web:build` del curso ejecuta `tsc` antes de Vite, y la CI lo ejecuta antes de `npm test`.

## La aplicación entera con WebDriver

[WebDriver](https://www.w3.org/TR/webdriver2/) es el protocolo del W3C que hay detrás de Selenium: un servidor que controla un navegador, aquí el webview de la aplicación. La documentación de Tauri describe dos vías:

- `tauri-driver`, un proxy hacia el driver de la plataforma: Microsoft Edge Driver en Windows, `WebKitWebDriver` en Linux. macOS no tiene driver para WKWebView, así que no hay macOS.
- [`tauri-plugin-wdio-webdriver`](https://crates.io/crates/tauri-plugin-wdio-webdriver) (1.4.0), un servidor WebDriver *dentro* de la aplicación, mantenido por el proyecto [WebdriverIO](https://webdriver.io/). Sin driver externo, y funciona en macOS.

El curso toma la segunda vía, detrás de una feature de Cargo, para que la aplicación que distribuyes no tenga puerto WebDriver (de [`src-tauri/Cargo.toml`, líneas 27-32](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/src-tauri/Cargo.toml#L27-L32)):

```toml
# Lección 21: un servidor WebDriver dentro de la aplicación, compilado solo para los tests end-to-end
tauri-plugin-wdio-webdriver = { version = "1.4.0", optional = true }

[features]
# `tauri build --features webdriver` compila el binario que controla WebdriverIO
webdriver = ["dep:tauri-plugin-wdio-webdriver"]
```

(de [`src-tauri/src/lib.rs`, líneas 49-51](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/src-tauri/src/lib.rs#L49-L51)):

```rust
    // Lección 21: ausente de los builds normales, así que la aplicación distribuida no abre ningún puerto WebDriver
    #[cfg(feature = "webdriver")]
    let builder = builder.plugin(tauri_plugin_wdio_webdriver::init());
```

`npm run build:e2e` ejecuta `tauri build --no-bundle --features webdriver` con el frontend Vite. La configuración de WebdriverIO arranca ese binario y espera a su servidor en el puerto 4445 (de [`e2e/wdio.conf.ts`, líneas 34-56](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/e2e/wdio.conf.ts#L34-L56)):

```ts
export const config: WebdriverIO.Config = {

  specs: ["./*.e2e.ts"],

```

El test escribe, hace clic y lee, y todo lo que hay en medio es real: la página, el IPC, las capabilities, el comando Rust (de [`e2e/chords.e2e.ts`, líneas 5-25](https://github.com/spareilleux/learn/blob/c34306b/code/rust-for-csharp-java/l16-tauri/e2e/chords.e2e.ts#L5-L25)):

```ts
describe("chord explorer", () => {
  // El servidor WebDriver puede responder antes de que se ejecute el script de la página: espera a
  // la lista de calidades, que la página rellena desde Rust cuando sus handlers están en su sitio
  before(async () => {
    await expect($("#qualities")).toHaveText(expect.stringContaining("Qualities:"));
  });

  it("spells the chord typed in the form", async () => {
    await $("#chord-input").setValue("Am7");
    await $("#chord-form button[type=submit]").click();

    await expect($("#chord-output")).toHaveText("Am7 (minor seventh): A C E G  —  1 b3 5 b7");
  });

  it("shows a Rust error when the quality is unknown", async () => {
    await $("#chord-input").setValue("Cm9");
    await $("#chord-form button[type=submit]").click();

    await expect($("#chord-error")).toHaveText("unknownQuality: unknown chord quality `m9` in `Cm9`");
  });
});
```

Cuatro cosas no funcionaron a la primera:

- `setValue` seguido de `browser.keys("Enter")` no enviaba el formulario: la salida seguía mostrando el acorde por defecto, `Bbm7 (minor seventh): Bb Db F Ab  —  1 b3 5 b7`. Hacer clic en el botón de envío hace lo que hace un usuario.
- La página de Tauri sobre WebDriver recomienda [`@wdio/tauri-service`](https://webdriver.io/docs/desktop-testing/tauri) (1.4.0). Con él, los mismos dos tests pasaron en 1 min 30 s en lugar de un segundo, con una advertencia antes de cada comando: `WARN tauri-service:window: Failed to get window states: Error: Tauri core.invoke not available after 5s timeout`. El servicio espera un segundo plugin, `tauri-plugin-wdio`, además de su paquete npm importado por la página, para su `browser.tauri.execute()` y sus mocks de comandos. El curso no necesita ninguna de las dos cosas, así que habla directamente con el servidor incrustado.
- En `ubuntu-latest`, la primera configuración esperó 20 s al servidor y se rindió con `Error: no WebDriver server on port 4445`. Allí la aplicación necesita unos 25 s para arrancar con una pantalla virtual; la configuración espera ahora hasta 60 s, como hace el servicio de WebdriverIO en CI, y se detiene enseguida si la aplicación termina.
- En `windows-latest` pasó lo contrario: el servidor respondió a los 394 ms, antes de que el script de la página hubiera enganchado sus handlers. El clic envió un formulario HTML normal, y el test leyó `Received: ""`. El hook `before` espera a un texto que la página solo escribe después de llamar a Rust. La máquina del autor nunca cayó en ese intervalo; dos runners de velocidades distintas sacaron a la luz ambos problemas de temporización.

## Firma de código

Ninguno de los instaladores de arriba está firmado. Windows lo dice:

```powershell
Get-AuthenticodeSignature "target\release\bundle\nsis\Chord Explorer_0.1.0_x64-setup.exe" | Format-List Status, StatusMessage
```

```text
Status        : NotSigned
StatusMessage : The file C:\Users\spare\source\repos\learn\code\rust-for-csharp-java\l16-tauri\target\release\bundle\nsis\Chord Explorer_0.1.0_x64-setup.exe is not digitally signed. […]
```

El curso no firma nada: un certificado cuesta dinero y pertenece a una persona o a una empresa. Lo que espera cada sistema, según las guías de distribución de Tauri (*por verificar*, nada de esto se ha probado aquí):

<Tabs syncKey="os">
<TabItem label="Windows">

Un instalador sin firmar descargado con un navegador provoca una advertencia de [SmartScreen](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation). La firma usa un certificado de firma de código OV o EV, o una clave en Azure Key Vault, configurados en `bundle.windows` (`certificateThumbprint`, `digestAlgorithm`, `timestampUrl`, o un `signCommand` propio). Desde 2024, un certificado EV ya no otorga reputación de inmediato: un archivo recién firmado puede seguir mostrando la advertencia hasta que gane reputación. Publicar en Microsoft Store exige firmar.

</TabItem>
<TabItem label="Linux / WSL">

No hay firma a nivel del sistema: un `.deb` o un `.rpm` lo firma el repositorio que lo distribuye (APT, DNF), y una AppImage puede llevar una firma GPG (`SIGN=1`, con `SIGN_KEY` y `APPIMAGETOOL_SIGN_PASSPHRASE` en el entorno de `tauri build`).

</TabItem>
<TabItem label="macOS">

Fuera de la App Store, una aplicación se firma con un certificado *Developer ID Application* y luego se **notariza**: se sube a Apple, que la analiza y devuelve un ticket que `tauri build` grapa al bundle. Ambas cosas requieren una membresía de pago del Apple Developer Program; con una cuenta gratuita, la aplicación solo se abre después de que el usuario se salte Gatekeeper. Las credenciales van en variables de entorno (`APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, y luego `APPLE_ID`, `APPLE_PASSWORD` y `APPLE_TEAM_ID`, o `APPLE_API_ISSUER`, `APPLE_API_KEY` y `APPLE_API_KEY_PATH` para una clave de API de App Store Connect).

</TabItem>
</Tabs>

## El updater

El [plugin updater](https://v2.tauri.app/plugin/updater/) (2.11.0) descarga una nueva versión y la instala. Su seguridad no depende de la firma de código de arriba sino de su propio par de claves, que genera la CLI:

```text
Your keypair was generated successfully:
Private: C:\Users\spare\AppData\Local\Temp\claude\C--Users-spare-source-repos-learn\515605f1-4f43-4be8-b806-602d45816b1f\scratchpad\updater-key\chord-explorer.key (Keep it secret!)
Public: C:\Users\spare\AppData\Local\Temp\claude\C--Users-spare-source-repos-learn\515605f1-4f43-4be8-b806-602d45816b1f\scratchpad\updater-key\chord-explorer.key.pub
---------------------------

Environment variables used to sign:
- `TAURI_SIGNING_PRIVATE_KEY`: String of your private key
- `TAURI_SIGNING_PRIVATE_KEY_PATH`: Path to your private key file
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`:  Your private key password (optional if key has no password)

ATTENTION: If you lose your private key OR password, you'll not be able to sign your update package and updates will not work
```

(`npx tauri signer generate --ci -p "" -w <file>`: `--ci` omite las preguntas y `-p ""` define una contraseña vacía, aceptable solo para una clave desechable como esta.)

El mecanismo, tal como está documentado (*por verificar*, la aplicación del curso no tiene updater):

1. La clave pública va en `tauri.conf.json` en `plugins.updater.pubkey`, con las URL que consultar en `endpoints`, y `bundle.createUpdaterArtifacts: true`.
2. Con la clave privada en `TAURI_SIGNING_PRIVATE_KEY`, `tauri build` escribe además un archivo `.sig` junto a cada instalador.
3. Publicas un archivo JSON en uno de los endpoints (el `latest.json` de una release de GitHub sirve) que indica, por plataforma, la versión, la URL de descarga y el contenido del `.sig`.
4. La aplicación llama a `check()` desde JavaScript o Rust, descarga la actualización, verifica la firma con la clave pública incrustada y la instala; en producción se exige HTTPS.

Si pierdes la clave privada, las aplicaciones instaladas ya nunca podrán aceptar una actualización: solo confían en esa clave.

## El móvil, en una sección

El proyecto Tauri 2 ya contiene lo que necesita el móvil: `#[cfg_attr(mobile, tauri::mobile_entry_point)]` sobre `run`, y `crate-type = ["staticlib", "cdylib", "rlib"]` en `src-tauri/Cargo.toml`, para que una aplicación Android o iOS pueda cargar la misma biblioteca. Los comandos, el estado, los eventos y las capabilities de las lecciones 17 a 20 son el mismo código. Lo que cambia, según la [documentación de Tauri](https://v2.tauri.app/start/prerequisites/#configure-for-mobile-targets) (*por verificar*, aquí no se ha ejecutado nada):

- `tauri android init` genera un proyecto Gradle en `src-tauri/gen/android`; necesita el SDK y el NDK de Android, y `tauri android dev` se ejecuta en un emulador o un dispositivo.
- `tauri ios init` genera un proyecto Xcode; necesita macOS y Xcode.
- El origen de la página pasa a ser `http://tauri.localhost` en Android (los tests simulados de la lección 17 ya lo eligen).
- Los plugins declaran las plataformas que admiten: dialog, fs y store existen en móvil, con diferencias documentadas en cada plugin; el sistema de archivos móvil está aislado en un sandbox.
- La vía WebDriver de esta lección es para escritorio; los tests end-to-end en móvil usan Appium o las herramientas de la plataforma.

## Puntos clave

- Cuatro niveles: `cargo test` para la lógica, el runtime simulado para los comandos a través del IPC, Vitest con `mockIPC` para el frontend, WebDriver para la aplicación entera. Cada uno detecta lo que el nivel inferior no puede.
- `mockIPC` responde a cualquier cosa que se le pida, y Vitest no comprueba los tipos: mantén `tsc` en el pipeline y un test end-to-end para el contrato.
- `tauri-plugin-wdio-webdriver` detrás de una feature de Cargo da un servidor WebDriver en Windows, Linux y macOS sin distribuirlo.
- `tauri build` produce instaladores nativos por sistema: 1,5 MB para NSIS y 2,2 MB para MSI en Windows, sin WebView2.
- La firma depende de cada sistema y cuesta un certificado o una membresía; el updater tiene su propio par de claves, y perder la clave privada rompe las actualizaciones para siempre.

## Ejercicios

1. Escribe un test Vitest para `api.diatonicChords` que compruebe el nombre del comando y sus argumentos. ¿Por qué el argumento se llama `tonicNote` y no `tonic_note`?

<details>
<summary>Solución</summary>

```ts
test("diatonicChords sends the tonic and the mode in camelCase", async () => {
  let received: unknown;
  mockIPC((cmd, args) => {
    if (cmd === "diatonic_chords") received = args;
    return [];
  });

  await api.diatonicChords("E", "minor");

  expect(received).toEqual({ tonicNote: "E", mode: "minor" });
});
```

`#[tauri::command]` convierte el parámetro Rust `tonic_note` a camelCase en el JSON que espera (lección 17). El test lo fija: si `api.ts` enviara `tonic_note`, este test fallaría, y el comando real se rechazaría por falta de un argumento.

</details>

2. Añade un test end-to-end que deletree `Am7`, haga clic en *+1* y compruebe el resultado. Antes de escribir el texto esperado, decide: ¿`A#m7` o `Bbm7`? ¿Por qué merece la pena un test end-to-end si `theory` ya tiene tests unitarios?

<details>
<summary>Solución</summary>

```ts
it("transposes up a semitone", async () => {
  await $("#chord-input").setValue("Am7");
  await $("#chord-form button[type=submit]").click();
  await $("#up").click();

  await expect($("#chord-output")).toHaveText("Bbm7 (minor seventh): Bb Db F Ab  —  1 b3 5 b7");
});
```

`theory` escribe la fundamental transpuesta con la grafía habitual: su test unitario `transposes_with_common_spellings` afirma que `Am7` subido un semitono es `Bbm7`, y la línea de salida es la que mostró la aplicación para `Bbm7` en la primera ejecución WebDriver fallida de arriba. Suponer `A#m7` habría hecho que el test afirmara lo que cree el autor en lugar del comportamiento del programa.

El test unitario demuestra la transposición; este test demuestra el cableado: el botón *+1* envía `semitones: 1` (no `"1"`, que la lección 17 mostró que se rechaza), la página lee el acorde del campo de texto, y el resultado sustituye a la salida. Nada de eso se ejecuta con `cargo test` ni con `mockIPC`.

</details>

3. Un compañero propone distribuir el build `webdriver`, "para que soporte pueda controlar la aplicación de un cliente". ¿Qué abre ese build, y qué le responderías?

<details>
<summary>Solución</summary>

El servidor incrustado escucha en un puerto TCP (4445 por defecto, o `TAURI_WEBDRIVER_PORT`) y acepta comandos WebDriver: buscar elementos, hacer clic, escribir, ejecutar scripts en la página. En escritorio, el servidor solo escucha en `127.0.0.1`; en Android escucha en todas las interfaces, para probar por Wi-Fi ([`src/server/mod.rs`, líneas 71-76](https://docs.rs/crate/tauri-plugin-wdio-webdriver/1.4.0/source/src/server/mod.rs)). Así que cualquier proceso de cualquier usuario de la máquina puede controlar la aplicación, actuando como la página: la sesión del usuario, sus archivos a través de la exportación, todo lo que concedan las capabilities.

Respuesta: no. Soporte necesita logs, una exportación de diagnóstico o una sesión remota que inicie el usuario. La feature existe para que el binario distribuido no contenga este servidor; la CI compila los dos y solo distribuye el que no lo tiene.

</details>
