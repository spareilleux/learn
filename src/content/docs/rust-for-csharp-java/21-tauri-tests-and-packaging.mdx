## The frontend with `mockIPC`

`@tauri-apps/api/mocks` replaces the IPC layer in a simulated DOM: `invoke` calls a function of the test instead of Rust. Vitest runs in the Vite configuration of lesson 19, with [jsdom](https://github.com/jsdom/jsdom) (from [`vite.config.ts`, lines 26-30](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/vite.config.ts#L26-L30)):

```ts
  test: {
    // A simulated DOM: no webview and no Rust, invoke is answered by mockIPC
    environment: "jsdom",
    include: ["src/**/*.test.ts"],
  },
```

A test checks what the page sends and how it reads the answer (from [`frontend/src/api.test.ts`, lines 11-22](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/frontend/src/api.test.ts#L11-L22)):

```ts
test("spellChord sends the symbol and returns the command's value", async () => {
  const calls: [string, unknown][] = [];
  mockIPC((cmd, args) => {
    calls.push([cmd, args]);
    return { symbol: "Am7", qualityName: "minor seventh", notes: ["A", "C", "E", "G"], intervals: ["1", "b3", "5", "b7"] };
  });

  const chord = await api.spellChord("Am7");

  expect(calls).toEqual([["spell_chord", { symbol: "Am7" }]]);
  expect(chord.notes).toEqual(["A", "C", "E", "G"]);
});
```

Lesson 18's channel works too: the mock receives the `Channel` object itself and can call its `onmessage` (from [`frontend/src/api.test.ts`, lines 37-44](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/frontend/src/api.test.ts#L37-L44)):

## The whole app with WebDriver

[WebDriver](https://www.w3.org/TR/webdriver2/) is the W3C protocol behind Selenium: a server that drives a browser, here the app's webview. Tauri's documentation describes two routes:

- `tauri-driver`, a proxy to the platform's driver: Microsoft Edge Driver on Windows, `WebKitWebDriver` on Linux. macOS has no WKWebView driver, so no macOS.
- [`tauri-plugin-wdio-webdriver`](https://crates.io/crates/tauri-plugin-wdio-webdriver) (1.4.0), a WebDriver server *inside* the app, maintained by the [WebdriverIO](https://webdriver.io/) project. No external driver, and it works on macOS.

The course takes the second route, behind a Cargo feature, so that the app you ship has no WebDriver port (from [`src-tauri/Cargo.toml`, lines 27-32](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/src-tauri/Cargo.toml#L27-L32)):

```toml
# Lesson 21: a WebDriver server inside the app, compiled only for end-to-end tests
tauri-plugin-wdio-webdriver = { version = "1.4.0", optional = true }

[features]
# `tauri build --features webdriver` builds the binary that WebdriverIO drives
webdriver = ["dep:tauri-plugin-wdio-webdriver"]
```

(from [`src-tauri/src/lib.rs`, lines 49-51](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/src-tauri/src/lib.rs#L49-L51)):

```rust
    // Lesson 21: absent from normal builds, so the shipped app opens no WebDriver port
    #[cfg(feature = "webdriver")]
    let builder = builder.plugin(tauri_plugin_wdio_webdriver::init());
```

`npm run build:e2e` runs `tauri build --no-bundle --features webdriver` with the Vite frontend. The WebdriverIO configuration starts that binary and waits for its server on port 4445 (from [`e2e/wdio.conf.ts`, lines 34-56](https://github.com/spareilleux/learn/blob/2ce5e72/code/rust-for-csharp-java/l16-tauri/e2e/wdio.conf.ts#L34-L56)):

The test types, clicks and reads, and everything between is real: the page, the IPC, the capabilities, the Rust command (from [`e2e/chords.e2e.ts`, lines 5-25](https://github.com/spareilleux/learn/blob/c34306b/code/rust-for-csharp-java/l16-tauri/e2e/chords.e2e.ts#L5-L25)):

The author's machine was never in that window; two runners of different speeds exposed both timing problems.

The course signs nothing: a certificate costs money and belongs to a person or a company. What each system expects, from Tauri's distribution guides (*to verify*, none of it tried here):

<Tabs syncKey="os">
<TabItem label="Windows">

An unsigned installer downloaded with a browser triggers a [SmartScreen](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation) warning. Signing uses an OV or EV code signing certificate, or a key in Azure Key Vault, configured in `bundle.windows` (`certificateThumbprint`, `digestAlgorithm`, `timestampUrl`, or a custom `signCommand`). Since 2024, an EV certificate no longer grants reputation immediately: a newly signed file can still show the warning until it builds reputation. Microsoft Store listing requires signing.

</TabItem>
<TabItem label="Linux / WSL">

No system-wide signing: a `.deb` or `.rpm` is signed by the repository that distributes it (APT, DNF), and an AppImage can carry a GPG signature (`SIGN=1`, with `SIGN_KEY` and `APPIMAGETOOL_SIGN_PASSPHRASE` in the environment of `tauri build`).

</TabItem>
<TabItem label="macOS">

Outside the App Store, an app is signed with a *Developer ID Application* certificate and then **notarized**: uploaded to Apple, which scans it and returns a ticket that `tauri build` staples to the bundle. Both require a paid Apple Developer Program membership; with a free account the app opens only after the user overrides Gatekeeper. The credentials go in environment variables (`APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, then `APPLE_ID`, `APPLE_PASSWORD` and `APPLE_TEAM_ID`, or `APPLE_API_ISSUER`, `APPLE_API_KEY` and `APPLE_API_KEY_PATH` for an App Store Connect API key).

</TabItem>
</Tabs>

## The updater

The [updater plugin](https://v2.tauri.app/plugin/updater/) (2.11.0) downloads a new version and installs it. Its security does not rely on the code signing above but on its own key pair, which the CLI generates:

```text
Your keypair was generated successfully:
Private: C:\Users\spare\AppData\Local\Temp\claude\C--Users-spare-source-repos-learn\515605f1-4f43-4be8-b806-602d45816b1f\scratchpad\updater-key\chord-explorer.key (Keep it secret!)
Public: C:\Users\spare\AppData\Local\Temp\claude\C--Users-spare-source-repos-learn\515605f1-4f43-4be8-b806-602d45816b1f\scratchpad\updater-key\chord-explorer.key.pub
---------------------------

Environment variables used to sign:
- `TAURI_SIGNING_PRIVATE_KEY`: String of your private key
- `TAURI_SIGNING_PRIVATE_KEY_PATH`: Path to your private key file
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`:  Your private key password (optional if key has no password)

ATTENTION: If you lose your private key OR password, you'll not be able to sign your update package and updates will not work
```

(`npx tauri signer generate --ci -p "" -w <file>`: `--ci` skips the prompts and `-p ""` sets an empty password, acceptable only for a throwaway key like this one.)

The mechanism, as documented (*to verify*, the course's app has no updater):

1. The public key goes in `tauri.conf.json` under `plugins.updater.pubkey`, with the URLs to check in `endpoints`, and `bundle.createUpdaterArtifacts: true`.
2. With the private key in `TAURI_SIGNING_PRIVATE_KEY`, `tauri build` also writes a `.sig` file next to each installer.
3. You publish a JSON file at one of the endpoints (a GitHub release's `latest.json` works) giving, per platform, the version, the download URL and the content of the `.sig`.
4. The app calls `check()` from JavaScript or Rust, downloads the update, verifies the signature against the embedded public key, and installs it; HTTPS is enforced in production.

Lose the private key and the installed apps can never accept an update again: they only trust that key.

## Mobile, in one section

The Tauri 2 project already contains what mobile needs: `#[cfg_attr(mobile, tauri::mobile_entry_point)]` on `run`, and `crate-type = ["staticlib", "cdylib", "rlib"]` in `src-tauri/Cargo.toml`, so that the same library can be loaded by an Android or iOS app. The commands, the state, the events and the capabilities of lessons 17 to 20 are the same code. What changes, according to the [Tauri documentation](https://v2.tauri.app/start/prerequisites/#configure-for-mobile-targets) (*to verify*, nothing run here):

- `tauri android init` generates a Gradle project in `src-tauri/gen/android`; it needs the Android SDK and NDK, and `tauri android dev` runs on an emulator or a device.
- `tauri ios init` generates an Xcode project; it needs macOS and Xcode.
- The page's origin becomes `http://tauri.localhost` on Android (lesson 17's mock tests already pick it).
- Plugins declare the platforms they support: dialog, fs and store exist on mobile, with differences documented per plugin; the mobile file system is sandboxed.
- The WebDriver route of this lesson is for desktop; mobile end-to-end tests use Appium or the platform's tools.

## Key takeaways

- Four levels: `cargo test` for the logic, the mock runtime for the commands through IPC, Vitest with `mockIPC` for the frontend, WebDriver for the whole app. Each catches what the one below cannot.
- `mockIPC` answers whatever it is asked, and Vitest does not type-check: keep `tsc` in the pipeline and an end-to-end test for the contract.
- `tauri-plugin-wdio-webdriver` behind a Cargo feature gives a WebDriver server on Windows, Linux and macOS without shipping it.
- `tauri build` produces native installers per system: 1.5 MB for NSIS and 2.2 MB for MSI on Windows, without WebView2.
- Signing is per system and costs a certificate or a membership; the updater has its own key pair, and losing the private key breaks updates for good.

## Exercises

1. Write a Vitest test for `api.diatonicChords` that checks the name of the command and its arguments. Why is the argument named `tonicNote` and not `tonic_note`?

<details>
<summary>Solution</summary>

```ts
test("diatonicChords sends the tonic and the mode in camelCase", async () => {
  let received: unknown;
  mockIPC((cmd, args) => {
    if (cmd === "diatonic_chords") received = args;
    return [];
  });

  await api.diatonicChords("E", "minor");

  expect(received).toEqual({ tonicNote: "E", mode: "minor" });
});
```

`#[tauri::command]` converts the Rust parameter `tonic_note` to camelCase in the JSON it expects (lesson 17). The test pins that: if `api.ts` sent `tonic_note`, this test would fail, and the real command would reject with a missing argument.

</details>

2. Add an end-to-end test that spells `Am7`, clicks *+1*, and checks the result. Before writing the expected text, decide: `A#m7` or `Bbm7`? Why is this worth an end-to-end test when `theory` already has unit tests?

<details>
<summary>Solution</summary>

```ts
it("transposes up a semitone", async () => {
  await $("#chord-input").setValue("Am7");
  await $("#chord-form button[type=submit]").click();
  await $("#up").click();

  await expect($("#chord-output")).toHaveText("Bbm7 (minor seventh): Bb Db F Ab  —  1 b3 5 b7");
});
```

`theory` spells the transposed root with the common spelling: its unit test `transposes_with_common_spellings` asserts that `Am7` up one semitone is `Bbm7`, and the output line is the one the app showed for `Bbm7` in the first failed WebDriver run above. Guessing `A#m7` would have made the test assert the author's belief instead of the program's behaviour.

The unit test proves the transposition; this test proves the wiring: the *+1* button sends `semitones: 1` (not `"1"`, which lesson 17 showed is rejected), the page reads the chord from the input, and the result replaces the output. None of that runs in `cargo test` or with `mockIPC`.

</details>

3. A colleague proposes shipping the `webdriver` build, "so that support can drive a customer's app". What does that build open, and what would you answer?

<details>
<summary>Solution</summary>

The embedded server listens on a TCP port (4445 by default, or `TAURI_WEBDRIVER_PORT`) and accepts WebDriver commands: find elements, click, type, run scripts in the page. On desktop the server binds to `127.0.0.1` only; on Android it binds to every interface, for testing over Wi-Fi ([`src/server/mod.rs`, lines 71-76](https://docs.rs/crate/tauri-plugin-wdio-webdriver/1.4.0/source/src/server/mod.rs)). So any process of any user on the machine can drive the app, acting as the page: the user's session, their files through the export, whatever the capabilities grant.

Answer: no. Support needs logs, a diagnostic export or a remote session the user starts. The feature exists so that the shipped binary does not contain this server; CI builds both and ships only the one without it.

</details>
