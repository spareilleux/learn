## The project question

An agent makes a playback computation faster. Has the guitarist heard the response sooner? [PM-005](../../product-management/pm-005-interpret-brutal-coexistence-experiments/) shows why a producer's own speed is insufficient. Here we use a concrete selected GA progression component and separate scheduling requests from event execution and output observation. [NET-008](../../network-science/net-008-map-clock-domains-before-ordering-events/) supplies the clock-domain checks.

## 1. A requested timer delay is not a measured callback time

At GA commit `76efbffd5af82b46c3146957a6bd4504008eeb89`, the [progression component](https://github.com/GuitarAlchemist/ga/blob/76efbffd5af82b46c3146957a6bd4504008eeb89/Apps/ga-dashboard/src/app/shared/progression.component.ts#L84-L116) uses [setTimeout](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timers) with accumulated chord durations. The HTML timer specification does not guarantee exact callback scheduling.

For an authored sequence, requested callback positions are 0, 1000 and 2000 ms; actual-like callback annotations are 12, 1080 and 2015 ms. These are invented records, not extracted traces.

### Exercise 1 — Separate deadlines from events

Calculate each callback's lateness and the two intervals between callbacks. Does requesting a 1000 ms spacing establish that the executed callbacks or audible chords have that spacing?

> **Answer.** Lateness is 12, 80 and 15 ms. Executed callback intervals are 1068 and 935 ms, despite requested intervals of 1000 ms. A request establishes neither execution spacing nor audio output. These authored differences do not diagnose the current machine.

## 2. A scheduled strum is another boundary

The [audio request code](https://github.com/GuitarAlchemist/ga/blob/76efbffd5af82b46c3146957a6bd4504008eeb89/Apps/ga-dashboard/src/app/shared/progression.component.ts#L140-L190) reads an audio-context time when the callback runs. It requests each sounding string at that anchor plus its physical string index times 0.03 seconds, using zero-based indices. Muted strings are skipped, but the remaining indices are not compacted.

For the authored fret list below, sounding indices are 1, 3 and 4:

```text
frets = [-1, 0, -1, 2, 3, -1]
```

### Exercise 2 — Preserve the requested sequence

Calculate the sounding strings' requested offsets and gaps. Would assigning consecutive ranks only to sounding strings preserve the source's requests? Are either set of numbers observed physical onsets?

> **Answer.** Offsets are 0.03, 0.09 and 0.12 seconds, with gaps 0.06 and 0.03 seconds. Compacting to ranks would instead request 0, 0.03 and 0.06 seconds, changing the schedule. Neither set is an observed physical onset. The selected source uses a triangle oscillator and an envelope, not a measurement of a real guitar.

## 3. Measure the endpoint the product promise names

The [authored trace table](https://github.com/spareilleux/learn/blob/main/code/streeling/evidence/tempo-clocks-2026-10-22/playback-endpoints.json) defines four sequential stages on one stipulated common millisecond clock: action to handler, handler computation to scheduling call, call to requested output boundary, and requested boundary to an authored output-onset annotation. There is no overlap between these intervals in this teaching model.

| Configuration | Handler dispatch, ms | Computation, ms | Scheduling wait, ms | Output beyond requested boundary, ms |
| --- | --- | --- | --- | --- |
| A | 4 | 4 | 72 | 10, 15, 20, 25 |
| B | 4 | 6 | 40 | 10, 15, 20, 25 |

The resulting action-to-output values are 90, 95, 100 and 105 ms for A; 60, 65, 70 and 75 ms for B. The output annotations and shared origins are authored premises, not actual acoustic captures or simultaneous observations of two configurations.

### Exercise 3 — Rank the right metric

Calculate the median computation and action-to-output durations for both configurations, and each paired difference. Which configuration is faster at each boundary? Does this establish a causal improvement in GA?

> **Answer.** Median computation is 4 ms for A and 6 ms for B. Median action-to-output duration is 97.5 ms for A and 67.5 ms for B; all four paired end-to-end differences are 30 ms. A computes faster while B has the smaller authored user-boundary duration. This illustrates endpoint dependence, not a measured or causal GA improvement. Deliberate scheduling wait is part of this defined interval and should remain visible.

## 4. A latency rule is only one approval condition

For this invented example, declare that every recorded action-to-output value must be at most 80 ms. A has no passing trial; B has four. Both ranges span 15 ms, so B has not reduced that particular spread descriptor. Four authored trials establish neither a production tail percentile nor perceptual acceptability.

### Exercise 4 — Make the bounded decision

Apply the 80 ms rule, compare the ranges and state what remains missing before recommending a new playback default to guitarists.

> **Answer.** A passes 0 of 4; B passes 4 of 4. Both ranges are 15 ms. Only B satisfies the declared latency-only rule on these invented records. An actual default decision still needs real matched acquisition, failures and missing-output records, effective browser/device state, sound-quality and intended-strum checks, repeated workload coverage and an appropriate musician/listener assessment. No real release is approved by these numbers.

## 5. Keep API estimates separate from a captured user outcome

The dated [Web Audio 1.1 Working Draft](https://www.w3.org/TR/2026/WD-webaudio-1.1-20260922/) defines processing and output-latency estimates with specific boundaries. They do not by themselves measure an action-to-acoustic-onset interval. The examined GA component requests oscillator starts and sets the highlighted step; it contains no output-onset acquisition. A highlighted chord or successful start request is not an audible-onset receipt.

### Exercise 5 — Prepare a comparison that could fail

Write a bounded real acquisition plan for a proposed playback change. Identify start/end events, clock mapping, source and effective mode, missing output, timing and musical guardrails, and a result that would reject the change. Compare a simpler measurement alternative to a new telemetry DSL.

> **Answer.** Pin source, browser/device, context lifecycle, effective output path, pattern and load. Define an input action and independently detected output onset with calibrated common timing or an explicit tested mapping; preserve detection thresholds, uncertainty, raw records and missing outputs. Repeat matched, order-balanced comparisons with a rule declared before acquisition, and check intended strum timing and sound quality. Reject a change that fails the declared latency/quality guardrails or whose comparison has invalid timing evidence. A common-clock loopback experiment may be simpler than a new DSL. It still needs actual calibration and validation; neither an instrument nor a telemetry contract was implemented here.
