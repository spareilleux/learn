## The project question

A GA developer wants an offline guitar render to remain comparable when execution moves between native code and [Node.js WebAssembly](https://nodejs.org/en/learn/getting-started/nodejs-with-webassembly). What does “same result” mean: identical source, float samples, or exported audio? This lesson separates these contracts so a successful file comparison cannot silently approve a stronger claim.

Read the [lab protocol](https://github.com/spareilleux/learn/blob/main/code/streeling/guitar-runtime/README.md), [runner](https://github.com/spareilleux/learn/blob/main/code/streeling/guitar-runtime/run.mjs), [source receipt](https://github.com/spareilleux/learn/blob/main/code/streeling/guitar-runtime/source.json) and [measured results](https://github.com/spareilleux/learn/blob/main/code/streeling/evidence/guitar-runtime-2026-10-22/results.json). The unchanged [GA Rust engine](https://github.com/GuitarAlchemist/ga/blob/dc2e74cbd992a298f67efb928b5b3754615e1924/Rust/guitar-web-wasm-demo/rust-engine/src/lib.rs) is pinned by revision and file hash. You will state the tested domain, distinguish equality from approximation, and identify the next experiment needed before broadening a claim.

## Pin the experiment before interpreting it

Both builds use that source: a native adapter and the [Rust target](https://doc.rust-lang.org/rustc/platform-support/wasm32-unknown-unknown.html) `wasm32-unknown-unknown`. The teaching commands use `rustc -O`; upstream Cargo release settings use `opt-level="z"` and LTO. Source identity therefore does not identify an upstream release binary. Compiler arguments, target and toolchain belong in the receipt alongside source hashes.

Each arm initializes a fresh profile 0 engine at 44100 Hz, requests E2 at 82.4069 Hz and velocity 0.1, then renders 176400 samples. Baseline keeps decay 0.9978. Candidate sets 0.9976 after initialization and before the note. These are separate treatments; compare native and WASM within each treatment before comparing treatments. A reproducible wrong assumption remains wrong, so write the expected relationship before opening results.

## Separate partitioning from runtime changes

The main native render uses one block; Node WASM uses 128-sample chunks. That comparison changes runtime and partition together. To test partitioning separately, fresh probes render a 4096-sample prefix as one block and as 128-sample partitions within each runtime. No note or parameter event occurs between blocks. All probe byte comparisons pass, and each fresh prefix matches its corresponding main render prefix.

This supports partition equality for those prefixes and event-free calls. It does not establish invariance over arbitrary lengths or events. In particular, applying a note between blocks changes the input sequence. A browser scheduler could also deliver events at different boundaries; this offline probe has no scheduler observation to settle that question.

### Practice exercise 3

Design a falsifier for extending the partition claim to parameter events without changing the current verdict.

> **Answer:** Define a sample-indexed event schedule before running, then render the same schedule under different partitions within a runtime. Split a block where an event falls inside it so both paths apply the event at the same sample. A differing byte sequence refutes that stronger claim. Merely placing an event at the next block boundary compares different inputs.

## Compare the representation you promise

The main native/WASM raw `f32` outputs differ at 2918 baseline samples and 2926 candidate samples. Maximum absolute difference is 2.9802322387695312e-8 for each arm. The evidence does not establish its cause. Do not assign it to an instruction, compiler optimization or mathematical function without an isolating experiment.

Yet PCM16 WAV bytes are equal between runtimes for each arm after `Math.round(sample * 32767)` quantization. Rounding maps multiple float values to the same integer. Equal exported bytes therefore coexist with unequal floats; they cannot prove identical internal floating state, which was not captured either.

A byte comparison is simple and decisive when the contract promises exact bytes. An error bound allows approximation but needs a documented domain, metric and rationale. Choosing the observed maximum afterwards as a product tolerance would turn a measurement into an unvalidated acceptance rule.

### Practice exercise 4

Write two verdicts, one for raw output and one for exported audio. What would justify a future error bound?

> **Answer:** Raw cross-runtime float equality is refuted for this run; quantized WAV byte equality is confirmed for each tested arm. A future bound needs a requirement established independently of this observation, representative cases and a stated failure criterion. Listening acceptability and musical equivalence require their own evidence; this export comparison supplies neither.

## Treat the adapter as part of the boundary

The runner constructs a fresh memory view after each render call, avoiding reliance on a view retained across calls that may change memory. The native adapter explicitly drops the engine allocation created by this pinned source's `Box::into_raw`. This source-specific cleanup is not a general ABI guarantee. WASM cases use fresh short-lived instances; allocation lifetime under repeated use remains untested.

Silence peaks are 0 and all 3 malformed-PCM negative controls are detected. These controls check the harness, not browser playback. Actual Node WebAssembly execution covers no AudioWorklet, device path, deadline, cancellation or listening test. The candidate improves reference decline error by 0.11416614959438576 dB, below its predeclared 1 dB gate; execution succeeds while `candidate_passes_decline_gate` remains false.

### Practice exercise 5

An agent proposes replacing the runner with a shared orchestration DSL. State a tradeoff and a rejection criterion before adopting it.

> **Answer:** A shared description might reduce duplicated experiment setup, but adds interpretation and provenance work. Keep it advisory until it preserves the commands, event schedule, raw and quantized evidence, and distinct execution and acceptance verdicts. Reject it if reproducing a mismatch requires reconstructing hidden defaults. First use the present runner and bounded cases; review memory lifecycle and browser behavior through separate experiments before any broader claim.
