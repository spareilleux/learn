A Learn authoring assistant wants to reuse an earlier analysis when the course identifier is unchanged. The source revision has changed, however, and the new analysis should differ. A high hit rate would then reward stale answers. Before adding memoization to a functional pipeline, ask whether the proposed key retains every premise on which the result depends.

Treat a cache key as a grouping rule on input records. Within each group, a correct pure cache must return the same result for every record. Search the finite catalogue for equal-key pairs with unequal results. A single witness rejects the candidate. Absence of a witness supports only this catalogue; it does not prove that all future inputs have been represented.

The fixed rows intentionally reuse an item name across revisions. Grouping by item alone merges different scores. The control adds revision to the key and separates that pair. Do not repair the first result by silently overwriting it after inspection: the collision is the evidence explaining why the original key was insufficient. Retain the old grouping alongside the proposed revision.

Python’s memoization documentation discusses argument-based keys and warns against caching unsuitable effects. It does not select a safe application key for GA, IX or Learn. Hidden locale, options, dependencies and mutable state can invalidate a superficially complete key. The codebook prerequisite retains interpretation context; here the new operation checks whether a projection of inputs is sufficient for reusing a result. A direct grouping table precedes any DSL helper, benchmark or caching policy.

### Exercise 1

Find the rejected key’s witness.

<details><summary>Answer 1</summary>

Rows `[0,1]` share item `x` but have scores `4` and `9`. Thus the item-only key is insufficient even though both records have plausible identities.

</details>

### Exercise 2

Apply the control key.

<details><summary>Answer 2</summary>

With fields `[item,revision]`, the witness list is `[]` and sufficiency is `true` for this catalogue. The conclusion is conditional on the declared pure results.

</details>

### Exercise 3

Would a unique key per row always be useful?

<details><summary>Answer 3</summary>

It avoids these collisions but can eliminate reuse. Correctness and hit rate are separate questions; first establish result preservation, then measure useful reuse on comparable work.

</details>

### Exercise 4

What if locale changes the score?

<details><summary>Answer 4</summary>

Add that premise to the input contract and search again. A revision field cannot stand in for an undeclared variable; do not call the existing control a universal key proof.

</details>

### Exercise 5

Why keep the uncached baseline?

<details><summary>Answer 5</summary>

It supplies the reference result for each original record. A cache judged only against its own earlier entries can repeat a stale result consistently while remaining wrong.

</details>
