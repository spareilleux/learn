A GA audio request can have an invalid rate, unsupported channel count and negative frame count at once. Returning only the first error sends the author through repeated correction cycles. Yet running dependent audio stages after failure would be wrong. Separate independent input inspection from dependent computation before choosing a composition operator.

The FSharp.Core reading defines what `Result.bind` does on an error. It does not promise to collect later errors. Our authored validation table therefore names a different operation: inspect every independent field, concatenate its error names and construct no accepted request until the list is empty. This is an interface design exercise, not a replacement for GA’s existing result module.

A tempting abbreviation is to evaluate every stage and collect its failures. That loses the independence premise: decoding samples may require a valid format first. Preserve the boundary in a proposed DSL by writing the dependency beside each check. More diagnostics are useful only if those diagnostics are meaningful and side effects have not already occurred.

## Fixed model and control

```json
{
  "values": {
    "sample_rate_hz": 0,
    "channels": 3,
    "frames": -1
  },
  "formula": "Validate fields independently in sample_rate_hz, channels, frames order: rate>0; channels in [1,2]; frames>=0. Concatenate error field names. Reject if any error; no effects occur.",
  "expected": {
    "errors": [
      "sample_rate_hz",
      "channels",
      "frames"
    ],
    "error_count": 3,
    "accepted": false
  },
  "negative_control": {
    "values": {
      "sample_rate_hz": 48000,
      "channels": 2,
      "frames": 64
    },
    "expected": {
      "errors": [],
      "error_count": 0,
      "accepted": true
    },
    "why": "Valid inputs remove every independent error without substituting defaults."
  },
  "assumptions": [
    "Pure total field checks; no check depends on another field being valid.",
    "Error order follows declared field order; frames is an integer."
  ],
  "limits": "Accumulation does not authorize dependent audio work or provide a GA implementation.",
  "input_types": {
    "sample_rate_hz": "integer",
    "channels": "integer",
    "frames": "integer"
  }
}
```

### Exercise 1

List the errors in the fixed case.

<details><summary>Answer 1</summary>

The ordered list is `[sample_rate_hz,channels,frames]`, with `3` errors. Each field independently violates its rule; order follows the contract, not discovery timing.

</details>

### Exercise 2

What would a fail-fast field chain return?

<details><summary>Answer 2</summary>

It would retain only `sample_rate_hz` under this order. That behavior can be correct for dependent computations, but it does not implement the requested complete diagnostic list.

</details>

### Exercise 3

Apply the valid control.

<details><summary>Answer 3</summary>

With `48000`, `2` and `64`, the list is `[]`, the count is `0` and the request is accepted. No default repaired an invalid value.

</details>

### Exercise 4

May a decoder run while these errors are collected?

<details><summary>Answer 4</summary>

Only if its own prerequisites are established separately. These pure field checks do not supply a valid buffer or authorize dependent effects.

</details>

### Exercise 5

What would refute an accumulation proposal?

<details><summary>Answer 5</summary>

Losing a field error, changing its identity, or constructing an accepted request while errors remain refutes the contract. Extra prose cannot compensate for a missing diagnostic.

</details>
