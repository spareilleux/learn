## The project question

A guitarist compares a score, a tablature and GA's note labels. An octave discrepancy may come from the notation's representation rather than the performance. [MusicXML 4.0 pitch](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/pitch/) stores a step, an optional chromatic alteration and an octave. Its [transpose element](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/transpose/) separately describes the adjustment from written pitch to sounding pitch. A parser can retain the note fields while losing the context that gives them their intended interpretation.

[WML-005](../../world-music-languages/wml-005-declare-note-name-conventions/) established a note-name convention. This lesson follows the next boundary: what does the encoded register mean? The examples are authored teaching cases, not a claim that every guitar file uses the same encoding.

## 1. Calculate the transposition declared by the file

For an ordinary single-note case without a doubling instruction, use the encoded note-number coordinate plus the [chromatic offset](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/chromatic/) plus 12 times the [octave change](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/octave-change/). The chromatic field excludes the octave-change contribution. These fixtures use integer semitones and the convention that C4 is MIDI 60.

The [fixed arithmetic](https://github.com/spareilleux/learn/blob/main/code/streeling/evidence/pitch-context-2026-10-22/transposition-arithmetic.json) gives encoded E3 as 52. With chromatic 0 and octave-change -1, sounding pitch is `52+0+12*(-1) = 40`, E2. A different file can encode E2 directly as 40 with no transposition; it already represents the same sounding pitch. The instrument label alone cannot decide between those representations.

### Practice exercise 1: follow the declared offset

Compare encoded E3 with chromatic 0 and octave-change -1 against encoded E2 with no transposition. Give the sounding note number in each case. Why must “guitar” alone not trigger another octave subtraction?

> **Answer:** Both give 40, E2. The first requires its declared offset; the second already has that register. Applying another automatic guitar offset would count the same intended adjustment again or alter an already concert-pitch representation.

## 2. Observe what the pinned parser actually preserves

Public GA commit `dc2e74cbd992a298f67efb928b5b3754615e1924` supplies [MusicXmlTypes](https://github.com/GuitarAlchemist/ga/blob/dc2e74cbd992a298f67efb928b5b3754615e1924/Common/GA.Business.DSL/Types/MusicXmlTypes.fs) and [MusicXmlParser](https://github.com/GuitarAlchemist/ga/blob/dc2e74cbd992a298f67efb928b5b3754615e1924/Common/GA.Business.DSL/Parsers/MusicXmlParser.fs). A fresh standalone load with installed SDK 10.0.113 executed their unchanged functions on the [ten inputs](https://github.com/spareilleux/learn/blob/main/code/streeling/evidence/pitch-context-2026-10-22/authored-xml-inputs.json). The [captured results](https://github.com/spareilleux/learn/blob/main/code/streeling/evidence/pitch-context-2026-10-22/native-parser-results.json) and [execution receipt](https://github.com/spareilleux/learn/blob/main/code/streeling/evidence/pitch-context-2026-10-22/execution.json) retain the scope.

An E3 score and an otherwise identical E3 score with the downward transpose produced structurally equal parsed scores. Both retained E3 and converted that retained pitch to 52. The parsed Attributes type has no transposition field. This is a reproduced information loss in that pinned helper, not a full application test or evidence about the current deployed service.

### Practice exercise 2: distinguish acceptance from preservation

Both scores return a successful parse and the same stored note number 52. Can the parsed record alone decide that the second score should sound at 40? What information is missing?

> **Answer:** No. The retained records are equal, but the original second score declares a downward octave transposition. The parsed record has lost that declaration. A successful result is insufficient evidence that sounding-pitch interpretation was preserved.

## 3. Keep clef appearance and declared transposition separate

MusicXML also has [clef-octave-change](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/clef-octave-change/), which belongs to a clef. The teaching probe added a value of -1 to the clef while retaining encoded E3. Its parsed record again equaled the base score: the helper retains the clef sign, not that octave metadata. This establishes another loss; it does not by itself settle every score producer's pitch policy.

Treat the encoded pitch, the instrument transpose and the clef's notation information as separate inputs to inspect. Do not blindly add both octave-looking fields as independent sounding-pitch offsets. A consumer needs an explicit encoding policy and representative import tests. Under the first fixture's declared transpose, subtracting the octave twice would turn 52 into 28, E1, instead of 40.

### Practice exercise 3: catch double application

The authored written E3 case declares a single downward octave adjustment. An importer subtracts 12 once for that declaration and once because it recognizes a guitar part. Give its output and the intended output. Does finding octave metadata in a clef justify this rule?

> **Answer:** It outputs 28, E1; the intended value is 40, E2. Clef octave metadata does not justify blindly applying a second instrument offset. Establish how the file encodes pitches and apply the intended transformation once.

## 4. Inspect losses inside an accepted note

The official [alter definition](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/alter/) allows fractional semitone alterations. The authored C4 input with alter 0.5 retained a pitch with alteration absent and helper note number 60. The pinned parser uses integer conversion; the input's fractional alteration did not survive. An integer alter 0 produced an explicit stored 0 instead, also converting to 60. Equal converted numbers do not establish equal retained records or lossless interpretation.

Two negative controls used step H and a missing octave. Both complete scores still returned success and retained one note, but that note had no pitch. The -999 values in the observation table are probe sentinels for absent fields, not musical notes returned by GA. These deliberately deficient inputs were not schema-validated and must not be presented as valid MusicXML documents.

### Practice exercise 4: inspect the nested outcome

For the fractional-alter case, what distinction disappeared? For the H case, how many notes and pitches survived? Can the outer success result certify preservation?

> **Answer:** The 0.5 alteration disappeared; absent alteration defaulted to 0 during conversion. The H case retained one note and no pitch. Outer success certifies neither preservation of the fractional alteration nor presence of a valid pitch in every retained note.

## 5. Choose a comparison that can detect the actual error

E3 at 52 and E2 at 40 both have pitch class 4. A pitch-class-only comparison therefore cannot detect this octave error. Preserve absolute register when the question concerns sounding notes, while retaining spelling and transposition provenance for notation questions. Tablature additionally needs tuning, string and fret conventions; a note number alone cannot reconstruct all of them.

The exercises propose import acceptance criteria without changing GA's production contract. A later implementation should preserve or explicitly reject unsupported context and validate the application path. No such correction or rendered-score comparison is included here.

### Practice exercise 5: design a discriminating check

An import check compares only pitch classes and accepts 52 where 40 was intended. Explain why it passes and give a check that fails on this case. State a boundary that remains untested.

> **Answer:** Both values reduce to class 4, so the check discards the differing octave. Comparing the intended absolute sounding number 40 against the actual 52 detects the error. A complete application import, rendered notation, playback and schema validation remain untested here.
