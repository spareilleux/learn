## The project question

A guitarist imports a practice phrase that changes tempo. Which seconds should its note boundaries occupy? [Standard MIDI Files](https://midi.org/standard-midi-files) exchange timed event data, but a retained event label is not a reconstructed timeline. [MCL-004](../../musicology/mcl-004-model-timing-without-inventing-a-style/) already examines an integer-tempo expression; [MCL-006](../../musicology/mcl-006-preserve-meter-grouping-and-tempo-units/) separates grouping and beat units. This lesson adds event locations, tempo integration and a control-flow check before claiming import success.

## 1. Declare the division and accumulate ticks

Use an authored single-track, quarter-note-based example with resolution Q = 480 ticks per quarter. [Mido's file documentation](https://mido.readthedocs.io/en/stable/files/midi.html) distinguishes track delta ticks from its other iteration coordinates. Accumulate every event's delta within its track before discarding or projecting events. Multi-track merging and simultaneous-event precedence require additional rules; they are not implemented here.

The authored tempo map is 500000 microseconds per quarter from tick 0, 1000000 from tick 480 and 250000 from tick 960. A tempo change affects subsequent positive tick intervals. The selected order is explicit at a shared boundary. Within one constant-tempo interval:

```text
delta_seconds = delta_ticks*microseconds_per_quarter / (Q*1000000)
```

### Exercise 1 — Recover the clock coordinate

For note boundaries at ticks 0, 240, 480, 720, 960 and 1200, calculate seconds from this map. Why is multiplying every tick by the last tempo invalid?

> **Answer.** The seconds are 0, 0.25, 0.5, 1, 1.5 and 1.625. The last-tempo shortcut gives only 0.625 seconds at tick 1200, because it applies the final rate to intervals governed by earlier tempos. A tempo value needs its location and a declared time division.

## 2. Split a note across tempo boundaries

A note begins at tick 240 and ends at tick 1200. Its duration crosses three constant-tempo pieces, with tick lengths 240, 480 and 240. Their elapsed times are 0.25, 1 and 0.125 seconds. These are authored score-to-time calculations, not a recorded performance or a swing model.

### Exercise 2 — Integrate the interval

Calculate the note duration by summing those pieces and by subtracting the absolute endpoint times. Does taking the tempo at note-on and applying it to the entire note give the same result?

> **Answer.** Both correct methods give 1.375 seconds: 0.25 + 1 + 0.125, or 1.625 - 0.25. Applying the initial 500000-microsecond rate to all 960 ticks gives 1 second and misses the intervening changes. The note interval must use the whole relevant tempo map.

## 3. Do not send a frame-based division through the quarter-note formula

[Microsoft's MIDI timing reference](https://learn.microsoft.com/en-us/windows/win32/multimedia/timing-information) distinguishes quarter-note and SMPTE divisions. For the limited non-drop-frame example here, 25 frames per second and 40 ticks per frame give 1000 ticks per second. A tempo event does not change that tick duration.

The encoded high byte for the negative format label -25 is 231. With low byte 40 the division word is `E728`. At GA commit `76efbffd5af82b46c3146957a6bd4504008eeb89`, the [header parser](https://github.com/GuitarAlchemist/ga/blob/76efbffd5af82b46c3146957a6bd4504008eeb89/Common/GA.Business.DSL/Parsers/MidiParser.fs#L13-L17) reads a nonnegative word; its [SMPTE branch](https://github.com/GuitarAlchemist/ga/blob/76efbffd5af82b46c3146957a6bd4504008eeb89/Common/GA.Business.DSL/Parsers/MidiParser.fs#L73-L85) negates the shifted high byte without first sign-decoding it. Static arithmetic predicts -231 for that source expression, not positive format label 25. This is not a fresh F# failure capture or a complete SMPTE decoder.

### Exercise 3 — Check the representation before using it

Under the declared 25-frame, 40-tick model, convert 750 ticks to seconds. Explain the distinction between encoded byte 231, signed label -25 and positive format label 25. May the source expression be used as a verified decoder?

> **Answer.** One tick lasts 0.001 second, so 750 ticks last 0.75 second. Byte 231 represents signed -25 after explicit signed-byte decoding; its negation gives format label 25. The selected source instead predicts -231 because it negates an unsigned high-byte value. That reading does not verify a working decoder. Drop-frame conversion is outside this example.

## 4. An event representation can lose the tempo's location

The [MIDI types](https://github.com/GuitarAlchemist/ga/blob/76efbffd5af82b46c3146957a6bd4504008eeb89/Common/GA.Business.DSL/Types/MidiTypes.fs#L19-L46) retain delta time on note records, while the tempo alternative holds only an integer. The selected [tempo-construction body](https://github.com/GuitarAlchemist/ga/blob/76efbffd5af82b46c3146957a6bd4504008eeb89/Common/GA.Business.DSL/Parsers/MidiParser.fs#L197-L207) supplies no event-time wrapper. Consider two authored streams with an initial tempo and note-on at tick 0:

| Stream | Delta before the change to 1000000 microseconds per quarter | Delta from that change to note-off | Absolute note-off tick | Note-off seconds |
| --- | --- | --- | --- | --- |
| A | 480 | 480 | 960 | 1.5 |
| B | 240 | 480 | 720 | 1.25 |

The initial tempo is 500000 microseconds per quarter. If correctly routed construction bodies projected these events to tempo integers and note-local deltas alone, both modeled lists would contain the same tempo values and the same note deltas. The lost tempo-event delta prevents recovering the difference. These hypothetical lists are **not actual parser outputs**.

### Exercise 4 — Show what the projection forgets

Calculate both absolute note-off ticks and seconds. Why can a later agent not recover which stream was supplied from the hypothetical projected lists alone?

> **Answer.** A ends at 480 + 480 = 960 ticks, after 0.5 + 1 = 1.5 seconds. B ends at 240 + 480 = 720 ticks, after 0.25 + 1 = 1.25 seconds. Dropping the tempo-event delta makes the modeled lists identical even though the intended locations differ. A later computation cannot uniquely recover an erased input. Correct dispatch alone would not fix this representation loss.

## 5. Check whether a selected body can be reached

The [event dispatcher](https://github.com/GuitarAlchemist/ga/blob/76efbffd5af82b46c3146957a6bd4504008eeb89/Common/GA.Business.DSL/Parsers/MidiParser.fs#L98-L173) first masks the status with a high-nibble mask, then later matches a full meta-event value. For a meta-event status:

```text
0xFF & 0xF0 = 0xF0
0xF0 != 0xFF
```

Thus the meta-event arm is unreachable through the shown match. The [fixed packet](https://github.com/spareilleux/learn/blob/main/code/streeling/evidence/tempo-clocks-2026-10-22/parser-boundaries.json) enumerates all 256 byte inputs; none produces the full meta-event label after that mask. This is a control-flow witness, not an execution of the parser on a valid file. Both parser pins used in MCL-004 and MCL-006 have identical bytes here; their metadata examples are now explicitly conditional body interpretations.

### Exercise 5 — State the next admissible claim

An agent cites the tempo body and declares a faithful MIDI-to-playback path. Give the byte-mask objection, distinguish the second representation issue, and specify what a real validation must retain and execute.

> **Answer.** The masked status cannot select the meta-event arm, so the shown path does not establish successful tempo parsing. Even with routing repaired, retaining tempo integers without their event locations loses information. A validated path needs timed events, raw tempo units, declared division, ordering/merge rules and exact source identity, then actual parser and timeline checks on boundary fixtures before playback measurement. A different library path would need its own evidence. No parser fix or working import was produced here.
