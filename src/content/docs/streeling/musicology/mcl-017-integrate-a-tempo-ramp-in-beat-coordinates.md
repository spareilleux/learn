An instruction to accelerate linearly is incomplete until its independent variable is named. A tempo linear in beat position is generally nonlinear in elapsed time. For a proposed [GA](https://github.com/GuitarAlchemist/ga) practice ramp, we integrate seconds per beat and compare the result with an endpoint-average shortcut. The course extends the prerequisite’s stepwise map with a distinct continuous model.

## Read the retained evidence

The playback reference defines tempo in quarter notes per minute. It does not declare our continuous interpolation policy. The retained phrase packet uses a fixed tempo; converting it to this ramp would be a new proposal requiring explicit event boundaries.

## Make the interpolation coordinate part of the proposal

A tempo mark at each endpoint does not determine the path between them. One editor might interpolate BPM over elapsed seconds, another over beat position, and another might interpolate duration per beat. All can pass an endpoint check while scheduling internal notes differently. The proposed record must name the interpolated quantity and coordinate, not merely retain the endpoint values and the word linear.

For this beat-based model, each small beat interval contributes its reciprocal local tempo to elapsed time. Slow portions receive more elapsed time per beat than fast portions. That asymmetry explains why the endpoint-average shortcut does not generally integrate the intended clock. The exact integral gives a reference for later numerical approximation, but it is not evidence that a real scheduler reaches the corresponding timestamps accurately.

The constant control is important because it makes the apparent singularity removable. A robust mathematical specification can state the limiting value explicitly instead of forcing a nonconstant formula through an undefined division. Near that limit a numerical implementation may need stable evaluation, which is a separate code concern. The direct derivation is enough to reject a shortcut before implementing anything. Only after preserving event positions, coordinate policy and the constant branch should a project consider a DSL node or an agent that creates ramped practice phrases.

### Exercise 1

Derive the BPM slope over the authored beat span. What coordinate does it use?

<details><summary>Answer 1</summary>

The listed slope is per quarter-beat position. Reusing it as BPM change per second would define another trajectory and generally another duration.

</details>

### Exercise 2

Derive elapsed time by integrating seconds per beat. Why does a logarithm appear?

<details><summary>Answer 2</summary>

Seconds per beat is the reciprocal of the linear tempo times the minute conversion. Its integral is logarithmic, yielding the displayed duration for this positive ramp.

</details>

### Exercise 3

Compare the endpoint-average shortcut with the integrated result.

<details><summary>Answer 3</summary>

The shortcut underestimates the authored duration. Averaging BPM and then taking its reciprocal is not the same as averaging the reciprocal along the beat interval.

</details>

### Exercise 4

Apply the constant-tempo control. Why must the implementation avoid dividing by zero slope?

<details><summary>Answer 4</summary>

The constant branch gives the stated duration and agrees with the shortcut. Directly using the nonconstant expression would be undefined even though the physical limit is finite.

</details>

### Exercise 5

What falsifies a claimed beat-linear conversion?

<details><summary>Answer 5</summary>

A reconstructed endpoint time inconsistent with the integrated duration rejects this model’s conversion. A different declared time-linear ramp must be assessed against its own equation instead.

</details>
