## Le post-traitement, dans trois outils

Le post-traitement dessine la scène dans une texture au lieu de l'écran, puis exécute des pixel shaders sur cette texture : bloom, anticrénelage, profondeur de champ, étalonnage des couleurs. Dans MonoGame, vous le faites à la main : `GraphicsDevice.SetRenderTarget` avec une [`RenderTarget2D`](https://docs.monogame.net/api/Microsoft.Xna.Framework.Graphics.RenderTarget2D.html), vous dessinez la scène, puis la texture sur un quad plein écran à travers un `Effect`. WPF applique un [`ShaderEffect`](https://learn.microsoft.com/dotnet/api/system.windows.media.effects.shadereffect) aux pixels rendus d'un élément, y compris ceux d'un `Viewport3D`.

three.js avait `EffectComposer` pour `WebGLRenderer` : une liste de passes, chacune un `ShaderMaterial` dessiné sur un quad. `WebGPURenderer` le remplace par [`RenderPipeline`](https://threejs.org/docs/pages/RenderPipeline.html), où les effets sont des nœuds TSL de la leçon 6, reliés en graphe.

| | MonoGame | three.js, `WebGLRenderer` | three.js, `WebGPURenderer` |
|---|---|---|---|
| La chaîne | votre code, target par target | `EffectComposer`, une liste de passes | `RenderPipeline`, un graphe de nœuds |
| Rendre la scène | `SetRenderTarget`, puis dessiner | `RenderPass` | `pass(scene, camera)` |
| Un effet | un `Effect` sur un quad | `UnrealBloomPass`, `ShaderPass(shader)` | `bloom(node)`, `fxaa(node)`, n'importe quel nœud TSL |
| Tone mapping et sRGB | votre dernier shader | `OutputPass`, ajoutée à la main | appliqués par le pipeline, sauf si `outputColorTransform = false` |
| À chaque image | `Draw` | `composer.render()` | `pipeline.render()`, au lieu de `renderer.render()` |

`RenderPipeline` s'appelait `PostProcessing` jusqu'à r183. L'ancien nom fonctionne toujours, avec un avertissement : « PostProcessing: "PostProcessing" has been renamed to "RenderPipeline". Please update your code to use "THREE.RenderPipeline" instead. » ([`PostProcessing.js`, lignes 5-20](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/PostProcessing.js#L5-L20)).

## Du bloom sur les repères

La touche reçoit cinq repères qui émettent de la lumière, avec une intensité émissive de 6 : bien au-delà de 1, la valeur la plus lumineuse qu'un pixel peut afficher après le tone mapping. Le bloom prend les pixels au-dessus d'un seuil, les floute à plusieurs tailles, et ajoute ce flou à l'image, si bien que les objets lumineux rayonnent comme à travers l'objectif d'un appareil photo ([lignes 46-62](https://github.com/spareilleux/learn/blob/8bf126b/code/threejs/src/07-post/main.ts#L46-L62)) :

```ts
// La chaîne, sous forme de graphe de nœuds : la texture de couleur de la passe de scène, le bloom ajouté par-dessus, puis la transformation de sortie
let pipeline: THREE.RenderPipeline | null = null;
let direct: THREE.DirectRenderPipeline | null = null;
const disposables: { dispose(): void }[] = [];
if (mode === 'bloom' || mode === 'bloom-fxaa') {
  pipeline = new THREE.RenderPipeline(renderer);
  const scenePass = pass(scene, camera);
  const sceneColor = scenePass.getTextureNode('output');
  const glow = bloom(sceneColor, 1.2, 0.4, threshold);
  disposables.push(scenePass, glow);
  if (mode === 'bloom') {
    pipeline.outputNode = sceneColor.add(glow);
  } else {
    // FXAA attend des valeurs sRGB après tone mapping : la transformation de sortie du pipeline est désactivée et appliquée avant FXAA
    pipeline.outputColorTransform = false;
    pipeline.outputNode = fxaa(renderOutput(sceneColor.add(glow)));
  }
}
```

`pass(scene, camera)` rend la scène dans une render target, et `getTextureNode('output')` est sa couleur, sous forme de nœud. [`bloom(node, strength, radius, threshold)`](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/BloomNode.js#L585-L597) vient de `three/addons/tsl/display/BloomNode.js` ; les addons comptent une cinquantaine de nœuds de ce genre dans le même dossier, de `fxaa` et `smaa` à `ssao`, `ssr`, `dof` et `outline`. `sceneColor.add(glow)` est du TSL : l'image finale est la scène plus son halo. Le pipeline rend ce graphe sur un quad plein écran, puis applique le tone mapping et la conversion sRGB du renderer, puisque `outputColorTransform` vaut `true` par défaut.

La boucle de la page appelle `pipeline.render()` au lieu de `renderer.render(scene, camera)` : la scène est rendue par la passe, à l'intérieur du pipeline.

- **Draw calls : 37 au lieu de 25.** Les 24 objets sont dessinés une fois, dans la passe de scène. Viennent ensuite 13 quads plein écran : un pour garder les pixels lumineux, cinq floutés horizontalement et cinq verticalement à des tailles divisées par deux, un pour les combiner, et le quad de sortie du pipeline. Par image, les `calls` comptent 14 rendus au lieu de 2.
- **Render targets : 12 au lieu de 1.** La passe de scène en a une ; `BloomNode` en crée onze, une pour les pixels lumineux, et une horizontale et une verticale pour chacune de ses cinq tailles ([`BloomNode.js`, lignes 156-180](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/BloomNode.js#L156-L180)). Ce sont des textures en demi-flottants, dimensionnées d'après le canvas : de la mémoire qui grandit avec l'écran.
- **Programmes : 13 au lieu de 4.** Chaque étape est un shader.

FXAA ajoute une passe, une render target et deux programmes. Le tableau vient de WebGPU. Sur le backend WebGL 2, les chaînes avec bloom comptent un programme de plus, 14 et 16, et sur les runners de CI sans GPU, qui rendent avec SwiftShader sur le CPU, le pixel du halo de FXAA donne 135, 176, 197 : 3 de plus qu'ici, au-delà de l'écart de 2 par canal qu'accepte `compare.mjs`. `check.sh` garde ces sorties WebGL 2 dans `expected/*.webgl.txt`.

### FXAA, après la transformation de sortie

FXAA lisse les bords crénelés en regardant le contraste entre pixels voisins, et « requires sRGB input », dit son code source : le tone mapping et la conversion sRGB doivent passer avant ([`FXAANode.js`, lignes 5-6](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/FXAANode.js#L5-L6)). La page désactive donc la transformation de sortie propre au pipeline, et l'applique dans le graphe avec `renderOutput`, avant `fxaa`. Dans ce mode, le renderer est créé avec `antialias: false` : le MSAA sur la passe de scène et FXAA après elle feraient deux fois le travail.

## DirectRenderPipeline : pas de passe de sortie

Même sans effet, `WebGPURenderer` rend dans une render target, puis la copie à l'écran par une passe de sortie qui fait le tone mapping et la conversion sRGB : la ligne `none` a 1 render target et 2 appels par image. r186 ajoute [`DirectRenderPipeline`](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/DirectRenderPipeline.js), qui « applies output processing directly in material shaders », évitant « the intermediate framebuffer and output pass », mais « changes blending and is not compatible with materials that sample the framebuffer, such as transmissive materials » ([lignes 6-20](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/DirectRenderPipeline.js#L6-L20)). Son `render` prend la scène et la caméra, contrairement à celui de `RenderPipeline` :

```text
$ node scripts/probe.mjs 07-post --query pipeline=direct

    "drawCalls": 25,
    "triangles": 2924

  "memory": {
    "geometries": 10,

    "programs": 4
  },
  "pipeline": "direct",
  "threshold": 1,

  "pixels": {
    "inlay at fret 5": "rgb(242, 250, 252)",
    "halo, 0.06 beside it": "rgb(53, 28, 20)",
    "neck, 0.15 beside it": "rgb(53, 28, 20)",
    "background": "rgb(12, 15, 20)"
```

Les mêmes quatre pixels que `none`, avec 0 render target et un appel par image. Les draw calls restent à 25, mais le 25e n'est plus un quad : un `scene.background` uni devient une sphère de 1 984 triangles dessinée derrière la scène ([`DirectRenderPipeline.js`, lignes 156-175](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/DirectRenderPipeline.js#L156-L175), et [`Background.js`, ligne 131](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/Background.js#L131)), d'où 2 924 triangles au lieu de 941. Sur un téléphone, une copie plein écran de moins par image peut compter ; mesurez-le sur l'appareil (*à vérifier*).

## Ce que libère dispose()

Un composant qui crée un pipeline doit le libérer quand il disparaît. Le mode `?dispose=` de la page libère après trois images et compte les render targets :

```text
$ node scripts/probe.mjs 07-post --query dispose=pipeline
{
  "frame": 4,
  "render": {
    "calls": 42,
    "drawCalls": 37,
    "triangles": 953
  },
  "memory": {
    "geometries": 10,
    "textures": 14,
    "programs": 12
  },
  "pipeline": "bloom",
  "renderTargets": {
    "before": 12,
    "afterPipelineDispose": 12
  }
}
```

```text
$ node scripts/probe.mjs 07-post --query dispose=all
{
  "frame": 4,
  "render": {
    "calls": 42,
    "drawCalls": 37,
    "triangles": 953
  },
  "memory": {
    "geometries": 10,
    "textures": 1,
    "programs": 2
  },
  "pipeline": "bloom",
  "renderTargets": {
    "before": 12,
    "afterPipelineDispose": 12,
    "afterNodesDispose": 0
  }
}
```

`pipeline.dispose()` libère un programme, le matériau de son quad de sortie, et aucune des 12 render targets : il ne libère que ce matériau ([`RenderPipeline.js`, lignes 162-169](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/RenderPipeline.js#L162-L169)). Les render targets appartiennent aux nœuds, et ne partent que lorsque la passe de scène et le nœud de bloom sont libérés eux aussi : il reste alors 0 render target, 1 texture et 2 programmes. Gardez donc une référence à chaque nœud qui possède une render target, et libérez-les avec le pipeline.

## À retenir

- Avec `WebGPURenderer`, le post-traitement, c'est `RenderPipeline` : un graphe de nœuds TSL qui commence par `pass(scene, camera)`, rendu par `pipeline.render()`. `PostProcessing` est son nom d'avant r183.
- Chaque effet coûte des draw calls, des programmes et des render targets qui grandissent avec le canvas : le bloom a ajouté ici 13 quads et 11 render targets.
- Les effets qui attendent du sRGB, comme FXAA, viennent après `renderOutput`, avec `outputColorTransform = false`.
- `DirectRenderPipeline` supprime la passe de sortie quand aucun effet n'est nécessaire, avec des limites sur le blending et la transmission.
- `pipeline.dispose()` ne libère pas les render targets des passes : libérez chaque nœud qui en possède une.

Les compteurs ne changent pas : les mêmes passes s'exécutent quel que soit le seuil.

<details>
<summary>Solution 2</summary>

`BloomNode` dimensionne ses targets à la moitié du drawing buffer (`_resolutionScale = 0.5`), puis divise la taille par deux à chacun de ses cinq niveaux ([`BloomNode.js`, lignes 322-341](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/BloomNode.js#L322-L341)). Les targets sont en `HalfFloatType`, quatre canaux de 2 octets chacun, sans depth buffer ([lignes 164-180](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/BloomNode.js#L164-L180)). En 3840 × 2160, la première target horizontale fait 1920 × 1080 × 8 octets : 16 588 800 octets, environ 16.6 MB. La target des pixels lumineux a la même taille, et les targets horizontale et verticale de chaque niveau font un quart de celles du niveau au-dessus : 1 + 2 × (1 + 1/4 + 1/16 + 1/64 + 1/256) ≈ 3.66 fois 16.6 MB, environ 61 MB pour le seul bloom, avant la passe de scène. Ces valeurs sont calculées à partir du code source, pas mesurées dans la mémoire GPU.

`setPixelRatio(2)` sur un canvas CSS de 1920 × 1080 donne le même drawing buffer de 3840 × 2160. Les pages de la leçon plafonnent le ratio à 2 ; `ThreeFretboard.tsx` de GA accepte jusqu'à 6, soit 36 fois les pixels d'un ratio de 1, et 9 fois ceux d'un ratio de 2.

</details>

```ts
import { pass } from 'three/tsl';

import { chromaticAberration } from 'three/addons/tsl/display/ChromaticAberrationNode.js';

const pipeline = new THREE.RenderPipeline(renderer);
const scenePass = pass(scene, camera);
const color = scenePass.getTextureNode('output');
const glow = bloom(color, 0.6, 0.6, 0.5);
const aberrated = chromaticAberration(color.add(glow));
pipeline.outputNode = aberrated;
```

La force, le rayon et le seuil sont ceux que ForceRadiant passe à `UnrealBloomPass` sur desktop. `chromaticAberration(node, strength = 1.0, center = null, scale = 1.1)` se trouve dans `three/addons/tsl/display/ChromaticAberrationNode.js` ([lignes 152-163](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/tsl/display/ChromaticAberrationNode.js#L152-L163)). Cette esquisse passe `tsc` avec les types de r186, mais n'a pas été rendue : la force qui correspond au `ShaderPass` de ForceRadiant est *à vérifier* sur la page. Gardez `scenePass`, `glow` et `aberrated` pour les libérer avec le pipeline.
