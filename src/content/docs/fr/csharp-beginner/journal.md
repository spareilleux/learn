## 2026-09-14 — Le SDK et les applications basées sur des fichiers

- Ma machine a deux SDK : 10.0.112 et 11.0.100-preview.3.26207.106. Sans [`global.json`](https://github.com/spareilleux/learn/blob/b19a296d6edc70be634ba147e27fd2d0c66f395f/code/csharp-beginner/global.json), `dotnet` choisit la préversion. Le dossier du cours fixe `10.0.100` avec `rollForward: latestFeature`, ce qui sélectionne ici 10.0.112.
- Le même jour, WinGet propose `Microsoft.DotNet.SDK.10` en version 10.0.401 : une bande de fonctionnalités plus récente que la mienne. La [page des applications basées sur des fichiers](https://learn.microsoft.com/dotnet/core/sdk/file-based-apps) indique que `#:include` est disponible à partir du SDK 10.0.300 ; la leçon 1 dit donc qu'une application basée sur un fichier tient en un seul fichier par défaut, et que `#:include` en ajoute d'autres à partir de ce SDK. Je n'ai pas essayé `#:include` : mon SDK est plus ancien.
- Les exemples sont des applications basées sur des fichiers plutôt qu'un projet par leçon : un débutant tape un fichier et l'exécute, sans rien configurer. Un simple `dotnet run app.cs` a pris 0,9 s la première fois et 0,2 s la suivante.
- Les autres fichiers `.cs` du même dossier ne sont pas compilés avec l'application : `hello.cs` a fonctionné à côté d'un fichier plein d'erreurs.
- **Les avertissements ne s'affichent que quand le SDK compile.** Un second `dotnet run` d'un fichier inchangé n'affiche aucun avertissement, et `dotnet run --no-cache` n'y change rien : il saute la vérification « à jour » de l'application basée sur un fichier, mais MSBuild trouve toujours la sortie compilée à jour et n'appelle pas le compilateur. Un `dotnet clean app.cs` avant chaque exécution fait revenir les avertissements ; [`check.sh`](https://github.com/spareilleux/learn/blob/b19a296d6edc70be634ba147e27fd2d0c66f395f/code/csharp-beginner/check.sh#L25-L50) le fait, et la leçon 3 le dit au lecteur.
- Les erreurs du compilateur vont sur la sortie standard, avec le chemin complet du fichier ; `The build failed. Fix the build errors and run again.` va sur la sortie d'erreur. `check.sh` fusionne les deux et ne garde que le nom du fichier, pour que les fichiers attendus soient les mêmes sur toutes les machines.
- Les erreurs de syntaxe cachent les autres : dans le programme cassé de l'exercice 2 de la leçon 1, la faute de frappe `Writeline` (CS0117) n'est signalée qu'une fois le `;` et le guillemet manquants corrigés. L'exercice repose là-dessus.
- Entrée standard : quand l'entrée vient d'un fichier, le texte tapé n'apparaît pas dans la sortie, donc les fichiers attendus contiennent les questions directement suivies des réponses. Les leçons montrent le terminal tel qu'une personne le voit, avec les lignes tapées, et le disent.
- Culture : la culture de mon Windows est `en-CA`. Avec `es-ES`, `double.TryParse("1.5")` renvoie `true` et 15, car le point sépare les milliers en espagnol ; avec `fr-FR`, il renvoie `false`. L'exemple fixe chaque culture explicitement, donc la sortie est la même sur tous les OS. Les autres exemples n'utilisent que des formats qui s'affichent de la même façon en `en-CA`, en `en-US` et dans la culture invariante du runner Linux.

## 2026-10-02 — Exceptions et sécurité face à null

- La leçon 8 attrape des exceptions avec `try` et `catch`, avec un diagramme des classes d'exception ; exécute `finally` après un `return`, après un `catch` et avant qu'une exception quitte la méthode ; lève une `ArgumentOutOfRangeException` avec `nameof` ; puis revient sur `null` : CS8600 et CS8618, `required`, l'opérateur `!`, et `WarningsAsErrors=nullable` défini avec `#:property`. Elle compte six exemples, quatre fichiers d'exercice (dont le point de départ de l'exercice 3, avec quatre avertissements) et cinq extraits refusés, dont les diagnostics sont CS0160, CS0165, CS0029, CS9035 et CS8602 en erreur. Le script utilisé pour les leçons 6 et 7 a vérifié les 28 blocs de code des trois langues contre `code/csharp-beginner` et `expected/`.
- Sous Windows, avec le SDK 10.0.112 et Git Bash, `check.sh` s'est terminé avec le code 0 et 102 lignes `ok`, dont les 15 fichiers `l08_*`. Ce n'est pas encore une exécution de la CI sur trois OS.
- La première exécution de la CI de la [PR #109](https://github.com/spareilleux/learn/pull/109) a échoué sous Linux seulement ([run 36968274101](https://github.com/spareilleux/learn/actions/runs/36968274101)) : le runner Linux a affiché les avertissements de `l08_null_warnings.cs` et `l08_ex_null_start.cs` dans l'ordre des lignes, alors que Windows, en local comme dans la CI, et macOS affichaient CS8618 en premier. Les messages eux-mêmes étaient identiques. `check.sh` place désormais les messages du compilateur en premier, les erreurs avant les avertissements, chaque groupe trié par ligne et colonne, et la leçon montre cet ordre. Aucun fichier attendu des leçons 1 à 7 n'a changé : leurs messages venaient déjà dans cet ordre.
- Surprises, toutes reprises dans la leçon : `throw "fret out of range";` donne CS0029, une erreur de conversion, là où j'attendais CS0155 (*The type caught or thrown must be derived from System.Exception*) ; `string capo = null;` sur une variable locale donne CS8600, pas CS8625, alors que le fichier de test de GA ci-dessous a reçu CS8625 pour un argument `null` ; dans `l08_null_warnings.cs`, CS8618 se trouve sur la déclaration de la propriété et la ligne qui plante n'a aucun avertissement ; `tuner off` s'affiche avant la valeur que renvoie `Tune`.
- Une phrase repose sur une sonde restée hors du code du cours : sans sa vérification, `NoteOfString(standard, 7)` échoue avec une `IndexOutOfRangeException`.
- Dogfooding au commit `5c3a52a` de GA, avec les hypothèses écrites avant de mesurer dans le tableau des expériences, et les sondes et leur mode d'emploi dans [`code/csharp-beginner/ga-probes`](https://github.com/spareilleux/learn/tree/main/code/csharp-beginner/ga-probes) :
  - `NoWarn` liste quinze avertissements de nullabilité dans [Directory.Build.props:21](https://github.com/GuitarAlchemist/ga/blob/5c3a52ab40d0d433f8f68dbbd0590f70c8d8cf26/Directory.Build.props#L21), et à nouveau dans [Directory.Build.targets:7](https://github.com/GuitarAlchemist/ga/blob/5c3a52ab40d0d433f8f68dbbd0590f70c8d8cf26/Directory.Build.targets#L7). J'attendais plus de 100 avertissements cachés dans GA.Domain.Core ; sans les deux listes, GA.Domain.Core et GA.Core n'en ont aucun. `ZzNullableCanary.cs`, sept erreurs de nullabilité ajoutées à GA.Domain.Core, a compilé sans avertissement avec les listes, et avec ses sept avertissements (CS8600 ×2, CS8602 ×3, CS8618, CS8625) sans elles. L'hypothèse est réfutée, et le tableau QA garde le constat : les listes ne cachent que les erreurs à venir.
  - `new Fret(50)`, `Fret.FromValue(50)` et `Fret f = 50;` lèvent tous une `ArgumentOutOfRangeException`, pour 50 et pour -2, comme prévu, et `Fret.TryCreate(50)` renvoie `Failure(Fret number must be between -1 (muted) and 36, got 50)`. Le message de l'exception nomme une constante privée, `GA.Domain.Core.Instruments.Primitives.Fret value (50) cannot be greater than _maxValue (36). (Parameter 'value')`, parce que [IRangeValueObject.cs](https://github.com/GuitarAlchemist/ga/blob/5c3a52ab40d0d433f8f68dbbd0590f70c8d8cf26/Common/GA.Core/Abstractions/IRangeValueObject.cs#L72-L74) le construit à partir des expressions de l'appelant, et son `ActualValue` reste vide.
  - La question ouverte du 2026-10-01 a sa réponse : `new PositionLocation(5, 3)`, avec la corde et la frette inversées sous forme de simples nombres, compile sans avertissement et construit la corde 5, frette 3.
