Les leçons 1 à 7 ouvraient une base de données, l'interrogeaient et la fermaient. Une application la garde ouverte, écrit depuis plusieurs threads, et s'arrête parfois au mauvais moment. Cette leçon demande ce que LadybugDB promet alors, et vérifie chaque promesse : dans un script Cypher, dans un script Bash qui lance et tue des processus de la CLI, et dans un programme Java avec plusieurs connexions et plusieurs threads.

| | SQL Server | DuckDB ([leçon 8](../../duckdb/08-persistence/)) | LadybugDB |
|---|---|---|---|
| Écrivains | plusieurs, avec des verrous de ligne et de page ; un écrivain attend les verrous dont il a besoin | plusieurs ; une mise à jour de la même ligne échoue aussitôt, une clé en double à la validation | **une seule transaction d'écriture dans toute la base de données** ; une autre est refusée aussitôt |
| Un lecteur pendant une écriture | attend sous `READ COMMITTED`, lit des versions de ligne sous `SNAPSHOT` | lit un instantané | lit un instantané |
| Une erreur dans une transaction | avec `XACT_ABORT OFF`, la plupart des erreurs n'annulent que l'instruction | la transaction est abandonnée : les instructions suivantes échouent, et `COMMIT` annule | **la transaction est annulée, et les instructions suivantes s'exécutent en auto-commit** |
| Le journal | le journal des transactions | un fichier `.wal`, jusqu'au prochain point de contrôle | un fichier `.wal`, jusqu'au prochain point de contrôle |
| Processus | clients d'un serveur | un processus en lecture-écriture, ou plusieurs en lecture seule | la même chose, dans la documentation |

Les trois scripts sont dans `code/ladybugdb`, et la CI compare leur sortie sur les trois systèmes d'exploitation :

- [`cypher/08-transactions.cypher`](https://github.com/spareilleux/learn/blob/main/code/ladybugdb/cypher/08-transactions.cypher), avec [`cypher/expected/08-transactions.csv`](https://github.com/spareilleux/learn/blob/main/code/ladybugdb/cypher/expected/08-transactions.csv), comme les scripts des leçons 1 à 4 ;

- [`java/src/main/java/graph/Transactions.java`](https://github.com/spareilleux/learn/blob/main/code/ladybugdb/java/src/main/java/graph/Transactions.java), avec [`java/expected-transactions.txt`](https://github.com/spareilleux/learn/blob/main/code/ladybugdb/java/expected-transactions.txt), et la même convention `# `.

## Auto-commit et transactions manuelles

Chaque instruction envoyée sans `BEGIN TRANSACTION` est une transaction à elle seule ([transactions](https://docs.ladybugdb.com/cypher/transaction/)). Une instruction qui crée deux projets, le second avec la clé primaire de `GA.Core` ([lignes 6-9](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/cypher/08-transactions.cypher#L6-L9)) :

```cypher
UNWIND ['New/Zero.csproj', 'Common/GA.Core/GA.Core.csproj'] AS path
CREATE (:Project {path: path, name: 'Zero'});
MATCH (p:Project) RETURN count(*) AS projects;
```

```text
Error: Runtime exception: Found duplicated primary key value Common/GA.Core/GA.Core.csproj, which violates the uniqueness constraint of the primary key column.
┌──────────┐
│ projects │
│ INT64    │
├──────────┤
│ 111      │
└──────────┘
```

Toujours les 111 projets de ga : `Zero`, créé avant l'erreur, a disparu avec le reste de l'instruction. Une transaction manuelle voit ses propres modifications, et `ROLLBACK` les annule ([lignes 11-16](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/cypher/08-transactions.cypher#L11-L16)) :

```cypher
BEGIN TRANSACTION;
CREATE (:Project {path: 'New/One.csproj', name: 'One'});
MATCH (p:Project) RETURN count(*) AS inside;
ROLLBACK;
MATCH (p:Project) RETURN count(*) AS after_rollback;
```

```text
┌────────┐
│ inside │
│ INT64  │
├────────┤
│ 112    │
└────────┘
┌────────────────┐
│ after_rollback │
│ INT64          │
├────────────────┤
│ 111            │
└────────────────┘
```

Créer une table et la charger font aussi partie de la transaction, comme la documentation le dit du DDL et de `COPY` ([lignes 18-24](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/cypher/08-transactions.cypher#L18-L24)) :

```cypher
BEGIN TRANSACTION;
CREATE NODE TABLE Package(name STRING PRIMARY KEY);
COPY Package FROM (LOAD FROM 'data/ga/package_refs.csv' (HEADER = true) RETURN DISTINCT package);
MATCH (k:Package) RETURN count(*) AS packages_inside;
ROLLBACK;
CALL show_tables() RETURN name ORDER BY name;
```

```text
┌─────────────────┐
│ packages_inside │
│ INT64           │
├─────────────────┤
│ 136             │
└─────────────────┘
┌─────────┐
│ name    │
│ STRING  │
├─────────┤
│ Project │
└─────────┘
```

136 paquets dans la transaction ; après l'annulation, plus de table `Package`, comme avec `CREATE TABLE` dans une transaction SQL Server ou DuckDB.

## Une erreur met fin à la transaction

Trois créations dans une transaction, la deuxième en double, puis `ROLLBACK` ([lignes 26-32](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/cypher/08-transactions.cypher#L26-L32)) :

```cypher
BEGIN TRANSACTION;
CREATE (:Project {path: 'New/Two.csproj', name: 'Two'});
CREATE (:Project {path: 'Common/GA.Core/GA.Core.csproj', name: 'Duplicate'});
CREATE (:Project {path: 'New/Three.csproj', name: 'Three'});
ROLLBACK;
MATCH (p:Project) WHERE p.path STARTS WITH 'New/' RETURN p.name;
```

```text
Error: Runtime exception: Found duplicated primary key value Common/GA.Core/GA.Core.csproj, which violates the uniqueness constraint of the primary key column.
Error: No active transaction for ROLLBACK.
┌────────┐
│ p.name │
│ STRING │
├────────┤
│ Three  │
└────────┘
```

**`Three` est dans la base de données, après un `ROLLBACK`.** L'erreur a annulé toute la transaction, `Two` compris, sans le dire ; `CREATE Three` s'est ensuite exécuté seul, en auto-commit, et a été validé ; `ROLLBACK` n'a trouvé aucune transaction. Un script qui compte sur son `ROLLBACK` final, ou sur son `COMMIT`, garde les instructions qui suivent l'erreur et perd celles qui la précèdent.

DuckDB s'arrête au même endroit, mais refuse les instructions qui suivent avec `Current transaction is aborted (please ROLLBACK)` : rien ne s'exécute par accident. SQL Server, avec `XACT_ABORT OFF`, n'annule que l'instruction en échec et garde la transaction ouverte. LadybugDB ne fait ni l'un ni l'autre.

D'autres erreurs font de même. Un `BEGIN` dans une transaction ([lignes 34-39](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/cypher/08-transactions.cypher#L34-L39)) :

```cypher
BEGIN TRANSACTION;
MATCH (p:Project {name: 'Three'}) DELETE p;
BEGIN TRANSACTION;
COMMIT;
MATCH (p:Project) WHERE p.path STARTS WITH 'New/' RETURN p.name;
```

```text
Error: Connection already has an active transaction. Cannot start a transaction within another one. For concurrent multiple transactions, please open other connections.
Error: No active transaction for COMMIT.
┌────────┐
│ p.name │
│ STRING │
├────────┤
│ Three  │
└────────┘
```

La suppression est annulée, et `COMMIT` n'a rien à valider. `CHECKPOINT` dans une transaction y met fin aussi ([lignes 47-52](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/cypher/08-transactions.cypher#L47-L52)) :

```text
Error: Found active transaction for CHECKPOINT.
Error: No active transaction for COMMIT.
┌────────┐
│ p.name │
│ STRING │
├────────┤
│ Three  │
└────────┘
```

`Five`, créé avant le `CHECKPOINT`, est perdu. Sur ma machine, une erreur de liaison (une propriété inconnue) et une erreur de catalogue (une table qui n'existe pas) dans une transaction se sont comportées de la même façon.

Une seule erreur ne met pas fin à la transaction : une écriture dans une transaction en lecture seule ([lignes 41-45](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/cypher/08-transactions.cypher#L41-L45)) :

```cypher
BEGIN TRANSACTION READ ONLY;
MATCH (p:Project) RETURN count(*) AS read_only;
CREATE (:Project {path: 'New/Four.csproj', name: 'Four'});
COMMIT;
```

```text
┌───────────┐
│ read_only │
│ INT64     │
├───────────┤
│ 112       │
└───────────┘
Error: Can not execute a write query inside a read-only transaction.
```

Le `COMMIT` réussit, en silence : la transaction était encore ouverte. L'exercice 1 écrit une fonction qui gère les deux cas.

## Deux connexions, un seul écrivain

Le programme Java ouvre une base de données en mémoire et deux connexions, `first` et `second`, sur le même objet `Database` : la concurrence que la [documentation](https://docs.ladybugdb.com/concurrency/) présente comme sûre. `execute` renvoie la première valeur d'un résultat, `ok`, ou l'erreur, que le résultat la signale ou que l'appel lève une exception ([lignes 134-144](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/java/src/main/java/graph/Transactions.java#L134-L144)). La première section ([lignes 18-28](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/java/src/main/java/graph/Transactions.java#L18-L28)) :

```java
print("first: BEGIN", execute(first, "BEGIN TRANSACTION"));
print("first: CREATE One", execute(first, "CREATE (:Project {path: 'New/One.csproj', name: 'One'})"));
print("first sees", execute(first, "MATCH (p:Project) RETURN count(*)"));
print("second sees", execute(second, "MATCH (p:Project) RETURN count(*)"));
print("second: CREATE Two", execute(second, "CREATE (:Project {path: 'New/Two.csproj', name: 'Two'})"));
print("first: COMMIT", execute(first, "COMMIT"));
print("second: CREATE Two", execute(second, "CREATE (:Project {path: 'New/Two.csproj', name: 'Two'})"));
```

```text
== 1. Two connections, one write transaction
first: BEGIN: ok
first: CREATE One: ok
first sees: 112
second sees: 111
second: CREATE Two: error: Cannot start a new write transaction in the system. Only one write transaction at a time is allowed in the system.
first: COMMIT: ok
second: CREATE Two: ok
```

`second` ne voit pas le projet non validé, et lit sans attendre. Son écriture est refusée **aussitôt** : pas d'attente du verrou, pas de délai d'expiration à configurer. Et le refus ne dépend pas de ce que touchent les transactions : `One` et `Two` sont des nœuds différents, et dans SQL Server, deux verrous de ligne. La documentation le dit : une seule transaction d'écriture à la fois, dans toute la base de données.

Une transaction en lecture seule lit un instantané, et ne bloque pas l'écrivain ([lignes 30-38](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/java/src/main/java/graph/Transactions.java#L30-L38)) :

```text
== 2. A read-only transaction reads a snapshot
second: BEGIN READ ONLY: ok
second sees: 113
first: CREATE Three: ok
first sees: 114
second sees: 113
second: COMMIT: ok
second sees: 114
```

Comme l'isolation `SNAPSHOT` de SQL Server : le décompte reste à 113 jusqu'à la fin de la transaction en lecture seule, pendant que `first` valide. L'erreur de la section 3 ([lignes 40-46](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/java/src/main/java/graph/Transactions.java#L40-L46)) se comporte depuis Java comme dans la CLI :

```text
== 3. An error ends the transaction
first: BEGIN: ok
first: CREATE Four: ok
first: CREATE GA.Core again: error: Runtime exception: Found duplicated primary key value Common/GA.Core/GA.Core.csproj, which violates the uniqueness constraint of the primary key column.
first: CREATE Five: ok
first: ROLLBACK: error: No active transaction for ROLLBACK.
new projects: [Five,One,Three,Two]
```

`Four` est perdu, `Five` validé.

## Un BEGIN refusé

Le refus ci-dessus visait une instruction en auto-commit, et `second` a continué normalement. Quand l'instruction refusée est `BEGIN TRANSACTION`, la connexion se casse. Le programme exécute ce cas dans un mode à part, `refused-begin` ([lignes 110-124](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/java/src/main/java/graph/Transactions.java#L110-L124)), parce que le programme s'arrête là sur deux des trois runners :

```java
print("first: BEGIN", execute(first, "BEGIN TRANSACTION"));
print("second: BEGIN", execute(second, "BEGIN TRANSACTION"));
print("first: COMMIT", execute(first, "COMMIT"));
System.out.flush();
print("second: MATCH", execute(second, "MATCH (p:Project) RETURN count(*)"));
print("second: BEGIN", execute(second, "BEGIN TRANSACTION"));
print("second: MATCH", execute(second, "MATCH (p:Project) RETURN count(*)"));
print("second: COMMIT", execute(second, "COMMIT"));
```

## Le fichier de base de données et son journal d'écriture anticipée

La suite de la leçon porte sur les fichiers et les processus, et `files.sh` pilote la CLI. Une CLI en lecture seule ne peut pas créer de base de données ([lignes 33-35](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/files/files.sh#L33-L35)), et une CLI en lecture-écriture qui charge ga et se termine laisse un seul fichier ([lignes 37-39](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/files/files.sh#L37-L39)) :

```text
== 1. A read-only CLI can't create a file
Cannot create an empty database under READ ONLY mode.
files: 
== 2. Create and load, then close
files: ga.lbdb 
```

Puis une CLI qui valide une création et reste ouverte, en lisant son entrée depuis une commande qui attend 20 secondes ([lignes 41-52](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/files/files.sh#L41-L52)) :

```bash
lbug --no_progress_bar --no_stats --mode csv "$D/ga.lbdb" > "$D/writer.txt" 2>&1 < <(
  echo "CREATE (:Project {path: 'New/One.csproj', name: 'One'});"
  sleep 20) &
writer=$!
# La validation écrit le WAL
wait_for "$D/ga.lbdb.wal"
```

```text
== 3. A process that stays open after a commit
files: ga.lbdb ga.lbdb.wal 
```

La validation a écrit `ga.lbdb.wal`, le journal d'écriture anticipée (*write-ahead log*). Le script attend ce fichier plutôt que la sortie de la CLI : quand sa sortie est redirigée vers un fichier, la CLI n'écrit rien avant de se terminer. La [page sur les fichiers sur disque](https://docs.ladybugdb.com/developer-guide/files/) décrit le journal tel que l'a trouvé la leçon 8 de DuckDB : créé par une transaction d'écriture validée, supprimé quand un point de contrôle réussit. Le point de contrôle s'exécute sur `CHECKPOINT`, à la fermeture de la base de données, et à la fin d'une transaction d'écriture dès que le journal dépasse `checkpoint_threshold`, que lit le script Cypher ([ligne 53](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/cypher/08-transactions.cypher#L53)) : 16777216 octets, 16 Mio, comme DuckDB.

## Un processus tué

`kill -9` sur l'écrivain, puis une nouvelle CLI sur le fichier ([lignes 54-59](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/files/files.sh#L54-L59)) :

```text
== 4. The same process, killed
files: ga.lbdb ga.lbdb.wal 
projects
112
files: ga.lbdb 
```

Le processus tué a laissé son journal. Le suivant l'a rejoué en ouvrant le fichier, `One` est là, et il a fait un point de contrôle à la fermeture : plus de journal. Une copie de `ga.lbdb` seul, prise pendant que le journal existe, manque les modifications validées ; copie les deux fichiers, ou exécute d'abord `CHECKPOINT`.

Un processus tué dans une transaction, après son `CREATE` mais avant tout `COMMIT` ([lignes 61-72](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/files/files.sh#L61-L72)) :

```text
== 5. Killed inside a transaction
files: ga.lbdb 
p.name
One
```

Pas de journal : une transaction non validée n'écrit rien sur le disque, donc rien ne montre qu'elle s'exécute, et le script ne peut qu'attendre 5 secondes. `Two` est perdu, comme la documentation le promet. Le programme Java ferme une `Database` dont la connexion a une transaction ouverte ([lignes 92-102](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/java/src/main/java/graph/Transactions.java#L92-L102)) :

```text
== 6. A database file
files: [ga.lbdb, ga.lbdb.wal]
BEGIN: ok
CREATE One: ok
files after close: [ga.lbdb]
reopened: [GA.Core]
```

La fermeture annule : `One` n'est pas dans le fichier rouvert.

## Deux processus sur un même fichier

La [page sur la concurrence](https://docs.ladybugdb.com/concurrency/) explique pourquoi ce n'est pas sûr, chaque `Database` met en cache des données qu'une autre ne peut pas rafraîchir, et dit que LadybugDB ne le permet pas. Il le permet, sous Windows, Linux et macOS : le lecteur répond depuis un état qui n'existe plus. S'il renvoie des données fausses, et pas seulement anciennes, quand il lit des pages qu'il n'avait pas en cache avant le point de contrôle est *à vérifier*.

Le message `Could not set lock` a une variante pour Linux et macOS, `Lock is held by PID …`, qui n'apparaît jamais : le code ferme le descripteur de fichier, puis demande à `fcntl` qui détient le verrou sur ce descripteur fermé, ce qui échoue ([lignes 147-172](https://github.com/LadybugDB/ladybug/blob/v0.20.4/src/common/file_system/local_file_system.cpp#L147-L172)). Le message de DuckDB nomme le processus ; celui de LadybugDB, non.

Sous Linux et macOS, les verrous `fcntl` appartiennent au processus : un deuxième verrou du même processus réussit, et deux objets `Database` en lecture-écriture fonctionnent sur un même fichier, avec deux caches. La règle que le verrou n'impose pas, donc : une seule `Database` par fichier et par processus, partagée par tous les threads, et aucun autre processus sur le fichier pendant qu'elle écrit.

`new Database(path)` ne déclare aucune exception, mais lève `java.lang.Exception`, une exception vérifiée, quand le fichier ne peut pas être ouvert : le code JNI la lève par sa classe ([`lbug_java.cpp`, lignes 618-636](https://github.com/LadybugDB/ladybug-java/blob/f2fb39f/src/jni/lbug_java.cpp#L618-L636)), ce que le compilateur Java ne peut pas voir. `catch (IOException e)` ne l'attrape pas, et `catch (Exception e)`, si ; la méthode `open` du programme l'attrape ainsi ([lignes 184-191](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/java/src/main/java/graph/Transactions.java#L184-L191)).

## À retenir

- Chaque instruction est une transaction ; le DDL et `COPY` dans une transaction manuelle sont annulés avec elle.
- **Une erreur dans une transaction manuelle l'annule et y met fin, en silence** : les instructions suivantes s'exécutent en auto-commit, et `ROLLBACK` ou `COMMIT` signalent `No active transaction`. Arrête-toi à la première erreur. Une écriture refusée par une transaction en lecture seule est l'exception : la transaction reste ouverte.
- Une seule transaction d'écriture dans toute la base de données : une deuxième est refusée aussitôt, quoi qu'elle touche. Les lecteurs voient un instantané et ne bloquent pas l'écrivain.
- Depuis Java, un `BEGIN` refusé casse la connexion : `Unknown Error` sous Windows, un plantage de la JVM sous Linux et macOS à la requête suivante. Retente le `BEGIN`, ou ferme la connexion.
- Les validations vont dans `.wal` jusqu'à un point de contrôle ; un processus tué laisse le journal, et l'ouverture suivante le rejoue. Une transaction non validée ne laisse rien.
- Le verrou de lecture-écriture n'arrête pas un processus en lecture seule sous Linux et macOS, et rien n'arrête un écrivain arrivé après un processus en lecture seule : le lecteur répond alors depuis un état ancien. Dans un processus, Linux et macOS acceptent deux objets `Database` en lecture-écriture sur un même fichier. Garde une seule `Database` par fichier, dans un seul processus.
- Une ouverture en lecture-écriture par une version plus récente met le fichier à niveau en silence ; `EXPORT DATABASE` et `IMPORT DATABASE` déplacent les données d'une version à l'autre.

## Exercices

Les solutions sont dans `Transactions.java`, sections 4 et 5, et leur sortie dans `java/expected-transactions.txt` : la CI les vérifie avec le reste.

1. Écris `String transaction(Connection connection, List<String> statements)` : elle exécute les instructions dans une seule transaction et les valide toutes, ou aucune. Elle renvoie `ok`, ou la première erreur. Teste-la avec une liste dont la deuxième instruction échoue, puis avec une liste valide, et affiche les projets qui existent.

<details>
<summary>Solution</summary>

[Lignes 146-161](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/java/src/main/java/graph/Transactions.java#L146-L161) :

```java
// Exercice 1 : toutes les instructions ou aucune. Un échec s'arrête avant l'instruction suivante, qui s'exécuterait en auto-commit
static String transaction(Connection connection, List<String> statements) {
    var begin = execute(connection, "BEGIN TRANSACTION");
    if (!begin.equals("ok")) {
        return begin;
    }
    for (var statement : statements) {
        var outcome = execute(connection, statement);
        if (outcome.startsWith("error") || outcome.startsWith("thrown")) {
            // Le moteur a déjà annulé ; ROLLBACK sert aux erreurs qui laissent la transaction ouverte
            execute(connection, "ROLLBACK");
            return outcome;
        }
    }
    return execute(connection, "COMMIT");
}
```

```text
== 4. Exercise 1: a transaction that stops at the first error
transaction: error: Runtime exception: Found duplicated primary key value Common/GA.Core/GA.Core.csproj, which violates the uniqueness constraint of the primary key column.
transaction: ok
new projects: [Five,One,Seven,Six,Three,Two]
```

Le premier appel crée `Six`, échoue sur `GA.Core`, et s'arrête : `Seven` ne s'exécute jamais, et `Six` est annulé par le moteur. Le second appel crée les deux. S'arrêter, c'est tout l'intérêt : une boucle qui continuerait validerait `Seven` seul. Le `ROLLBACK` après une erreur signale en général `No active transaction`, et son résultat est ignoré ; il est là pour les erreurs qui laissent la transaction ouverte, comme une écriture dans une transaction en lecture seule. Le test d'erreur couvre aussi `thrown` : une exception du code JNI, comme `Unknown Error`, est une erreur.

</details>

2. Huit threads, chacun avec sa propre connexion sur la même `Database`, créent 25 projets chacun, une transaction par projet, avec `transaction` de l'exercice 1. Écris `withRetry`, qui retente une transaction refusée parce qu'une autre est en train d'écrire, et vérifie que les 200 projets sont là.

<details>
<summary>Solution</summary>

[Lignes 163-176](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/java/src/main/java/graph/Transactions.java#L163-L176), et les threads aux [lignes 58-80](https://github.com/spareilleux/learn/blob/93f6f82/code/ladybugdb/java/src/main/java/graph/Transactions.java#L58-L80) :

```java
// Exercice 2 : retenter une transaction que le moteur refuse parce qu'une autre est en train d'écrire
static int withRetry(Callable<String> transaction, AtomicInteger failures) throws Exception {
    for (int retries = 0; ; retries++) {
        var outcome = transaction.call();
        if (!outcome.contains("Only one write transaction at a time")) {
            if (!outcome.equals("ok")) {
                throw new IllegalStateException(outcome);
            }
            return retries;
        }
        failures.incrementAndGet();
        Thread.sleep(1 + ThreadLocalRandom.current().nextInt(5));
    }
}
```

```text
== 5. Exercise 2: eight threads that write
thread projects: 200
```

Les 200 projets, sur les trois runners. Le nombre de refus n'est pas comparé : 153 sous Windows, 155 sous Linux et 24 sous macOS dans l'exécution de CI de `93f6f82`. Une pause aléatoire de 1 à 5 millisecondes évite que les threads retentent en même temps. Toute autre erreur termine le thread par une exception, au lieu d'être retentée indéfiniment.

Les refus viennent de `BEGIN TRANSACTION`, et l'instruction suivante sur la connexion est le `BEGIN` de la nouvelle tentative : le schéma qui survit au bug du `BEGIN` refusé sur les trois OS. `ExecutorService` est `AutoCloseable` depuis Java 19 : le `try`-with-resources attend les huit tâches, et `invokeAll` renvoie leurs nombres de tentatives.

</details>
