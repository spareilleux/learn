## A small, auditable cadence

Start with **one English module per week**, not a bulk import or an autonomous batch. CS-002 is a useful first candidate because it already names a cycle, makes checkable repo claims, and includes Python/YAML snippets. This is a proposed review order, not a claim that CS-002 is ready. For each module:

1. **Freeze the input.** Record the full Demerzel commit, exact source path, research-cycle ID if present, and the learn commit that imports it. If the cycle or production record is absent, record that absence. Compare every factual claim with first-party docs or pinned repository source; write a question and a possible falsifier before testing. The existing [sync lock](https://github.com/spareilleux/learn/blob/ae30a24dde3904ec5fbf0e104b5dbd59508e7070/streeling.lock.json) and source links supply part of this chain, not claim-level verification.
2. **Study and run the examples.** Keep source code for executable snippets under `code/streeling/<module>/`, with a deterministic command, dependencies/versions, expected transcript, and a CI job that actually runs it on relevant OSes. For CS-002, test the examples and compare its assertions about Demerzel's loop policy against the pinned [policy](https://github.com/GuitarAlchemist/Demerzel/blob/c72fb746116346ce1991a4f108cd12f5e012e3fb/policies/autonomous-loop-policy.yaml). A syntactic pass is narrower than a proof of the lesson's general claims. Record exact commands, output, platform, and bounds; an unrun snippet remains “to verify.”
3. **Review before promoting status.** A named reviewer checks source-to-claim mapping, scope of each test, links, and the dated journal entry. Use four independent labels: `generated` for imported AI text, `studied` for an author's dated reading note, `tested` for a specified claim with retained execution or source evidence, and `disproved` for a claim contradicted by a reproducible counterexample. A module can contain claims in several states; do not promote the whole module because one example passed. Keep refutations visible, with the previous wording and evidence. The existing [Petri journal's QA and Experiments tables](https://github.com/spareilleux/learn/blob/ae30a24dde3904ec5fbf0e104b5dbd59508e7070/src/content/docs/petri-nets/journal.md) show the site's house style: expectation, observed result, pinned `file:line`, measure, verdict, and dated entry.
4. **Publish the reviewed batch and feed it back.** Keep generated source pages and their caution intact. Add a dated entry in the hand-written Streeling journal with a claim ledger and linked code/CI artifact; only mark a module studied after actual study. A verified correction belongs in the source Demerzel module (then re-sync from its exact commit), while a reproducible upstream defect gets a narrowly scoped issue in its owning repo with source SHA, minimal reproduction, expected/actual result, and the learn journal link. Mark invalidated hypotheses as such; do not delete their record. Translate reviewed prose only after the English claim and example settle, and keep locale status no stronger than the underlying evidence.

Advance the next module only after that chain is reviewable. Separately decide whether Demerzel research should resume as a manual, bounded cycle or through a repaired scheduler; the current workflow cannot supply a trustworthy cadence. The intended [pipeline](https://github.com/GuitarAlchemist/Demerzel/blob/3ebf61060d7b57a9df3bcb4a53e3c8115dc35281/.claude/skills/seldon-course-pipeline/SKILL.md) already calls for review and a production log, but the observed artifacts do not prove those gates have run. Before claiming success on a future publication, verify the exact live page and journal, source SHA, example run, reviewer decision, and any upstream issue or correction independently.
