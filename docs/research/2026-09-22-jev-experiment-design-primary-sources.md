## Local harness audit: three distinctions to preserve

These are read-only observations of the existing `code/typesafe-ai-system-one/` sources as they stood during this review, not Jev results.

1. `typesafe_lab.py` and `jev_benchmark.py` name `len(encode_payload(...))` an estimated token upper bound. `encode_payload` returns UTF-8 bytes, so the direct measurement is **request-body bytes**. It is a useful preflight size proxy, but no first-party source reviewed here proves that it upper-bounds provider-billed input tokens, including any server-side framing. Rename or qualify the metric before presenting a hard dollar guarantee. Actual billed input is learned only from API usage/account billing after a call.
2. The current `requests_for()` constructs a batched state containing all 12 cases, but each singleton state contains only its own case. Thus a batched-versus-singleton ratio changes **both state size and batching**. It cannot isolate the batching mechanism demonstrated by the official cookbook. A clean batching A/B uses the same full state in every request, changing only whether the 12 questions are packaged together. A separate per-case-state arm can test whether smaller context improves quality or cost.
3. In the current batch, every question refers to its target case by ID within a shared 12-case state. This is a reasonable hypothesis but carries the documented indirection/distractor risk. Compare per-case-state quality, not only dollars. An explicit case ID in the question is not proof that the model ignored other cases or prompt-injection text.

## Three experiments, ordered by cost and authority

| Stage | Question and design | Required evidence | Stop/reject condition |
| --- | --- | --- | --- |
| 0. Local, no provider | Can the schema validator, labels, scoring and fail-closed routing handle a fixed set of supported/contradicted/insufficient, multilingual, missing-evidence, and injected-text fixtures? Use deterministic mock responses; freeze fixture bytes and labels before writing thresholds. | Test output, fixture digests, scorer results explicitly labeled **mock**, and validation of malformed responses. | Any case can trigger authority or side effects from a mock answer; any missing telemetry is silently treated as zero. |
| 1. Bounded Jev quality pilot, only after separate cost/credential approval | Ask the same narrow evidence question with `jev-1.13.0` over sanitized labeled cases. Pre-register pass/fail and false-support criteria. Compare (a) one case per state and (b) many cases in a shared state, keeping question wording stable. This assesses distractor/indirection effects; it does not yet prove token savings. | Exact model, request SHA-256, input/output usage, per-case distribution, latency, error/retry count, accuracy, false-supports, calibration and actual rate-card dollars. | Any unsafe false support in the small pilot, unexpected model, exceeded call cap, or account billing uncertainty that the operator is unwilling to accept. |
| 2. End-to-end savings, only after quality pilot | Compare current deterministic/LLM path with a Jev filter plus the **same** downstream model, prompts, cache regime and human gate. Count Jev, preprocessing, downstream input/output/reasoning/cache tokens, retries and fallbacks. Run a separate pure-batching comparison with identical state in both arms. | Dollar cost per successful task, false-accept rate, latency distribution, frontier calls/tokens avoided, language slices and confidence intervals on held-out cases. | No supported net dollar saving after realistic caching, quality regression, high escalation rate, or a result dependent on hand-tuned test thresholds. |

The Stage 1 single-request price estimate is `reported_input_tokens × 0.042 / 1,000,000` USD under the reviewed Jev 1.13 price card. This is **not** an account-charge statement: any promotional credit, tax, minimum, changed rate, or other billing rule needs account-side verification. A local preflight cap can prevent known oversized payloads; it cannot mathematically guarantee a provider charge ceiling without a documented tokenizer and account-level spending control.

## Good and poor first applications

The best first independent test is **non-authoritative evidence or passage routing**: a deterministic retriever finds candidates, Jev judges a narrow semantic property, and code decides what context a fixed answerer sees. The [official RAG example](https://docs.typesafe.ai/cookbooks/classifying_rag_passages) demonstrates that shape, not its validity for GA, Gaia, IX, or Demerzel. IXQL/DuckDB is a plausible future measurement sink for per-item results, but neither source establishes a Jev connector or savings for IX; that remains a repository-specific hypothesis.

Avoid asking Jev to grant merge/spend/deploy authority, verify cryptographic identity, count exact items, compare dates, compute token budgets, execute IXQL, or replace a generative coding agent. These either require deterministic code/independent authority or conflict with TypeSafe's [documented weaknesses](https://docs.typesafe.ai/model-jaggedness/jev-1.13). The vendor's statement that typed results avoid free-text output proves a constrained response shape, not semantic correctness.

## Open checks before any live experiment

- Confirm the account's current credits and spending controls in the console without copying any key into a document or log; no public source here answers that account-specific question.
- Recheck model ID, price, context, rate limits and SDK version immediately before the call.
- Decide which sanitized repository fixtures can legally and safely leave the machine. No private code or secrets by default.
- Fix or clearly relabel the byte-based preflight metric and separate the pure batching arm from the per-case-state quality arm.
- Obtain a bounded operator approval for any paid call; this research pass made none.
